P2 — SHOULD FIX:

  lib/admin/getFailureAlerts.ts:55-60  🐢 P2: New `where:` predicate on an UNINDEXED column —
  `NotificationLog.attemptCount`.

    Added:
      prisma.notificationLog.count({ where: { status: 'failed', attemptCount: { gte: MAX_ATTEMPTS } } })
      prisma.notificationLog.count({ where: { status: 'failed', attemptCount: { lt:  MAX_ATTEMPTS } } })

    Index inventory for `NotificationLog` (`prisma/schema.prisma`, cross-checked against
    `prisma/migrations/20260602080000_notification_dispatcher/migration.sql:16,20` and
    `20260518052219_booking_v1/migration.sql:68`):
      @@unique([bookingId, template])   → NotificationLog_bookingId_template_key
      @@index([bookingId])              → NotificationLog_bookingId_idx
      @@index([template, scheduledFor]) → NotificationLog_template_scheduledFor_idx
      @@index([status, nextAttemptAt])  → NotificationLog_status_nextAttemptAt_idx
    `attemptCount` appears in NO index.

    Plan consequence: the planner can use only the `status` prefix of
    `NotificationLog_status_nextAttemptAt_idx`, then must heap-fetch every matching row to
    evaluate `attemptCount`. Not an index-only scan. So each count reads the ENTIRE
    `status='failed'` partition, and this PR runs TWO of them — where master ran one.

    Why it compounds rather than stays flat:
      - There is no retention or purge path for `NotificationLog` anywhere in the repo
        (grepped `lib/jobs/**`, `app/api/cron/**`; `retentionSweeper` covers only the Issue 090
        customer-anonymize and operator-document windows, not notification rows). Permanently
        dead rows (`attemptCount >= 5`) are never deleted by design — they ARE the dead-letter
        record. So the `status='failed'` partition is monotonically growing and the scan cost
        grows linearly with the lifetime count of failed deliveries.
      - The queries run on every `/admin` render (see P3 caching gap below), not on a cron.

    Fix (preferred): add `@@index([status, attemptCount])` to the `NotificationLog` model.
    Both counts then become index-only scans and the heap fetch disappears entirely.
    Per the Issue 007 rule this index is expressible in the Prisma DSL, so it must be declared
    in BOTH `prisma/schema.prisma` AND the migration SQL — not raw-SQL-only.
    Alternative (no migration): collapse the two scans into one — see P3 below.

    Severity note: rated P2 rather than P1 because the call site is `lib/admin/**` behind an
    authenticated admin console (low request volume), not `app/api/**` on a customer hot path.

P3 — ADVISORY:

  lib/admin/getFailureAlerts.ts:55-60  ℹ️  P3: Two sequential scans of the same partition.
    `count(status='failed' AND attemptCount >= 5)` and `count(status='failed' AND attemptCount < 5)`
    are complements over an identical row set, executed as two independent queries. One pass
    can produce both:
      SELECT count(*) FILTER (WHERE "attemptCount" >= $1) AS dead,
             count(*) FILTER (WHERE "attemptCount" <  $1) AS retrying
      FROM "NotificationLog" WHERE "status" = 'failed'::"NotificationStatus"
    Halves the work whether or not the index from the P2 above is added. Trade-off: drops to
    `$queryRaw`, which loses the Prisma typing that the new unit test currently asserts against
    (`toHaveBeenCalledWith({ where: … })`) — so prefer the index fix unless a migration is
    unwelcome.

  app/admin/(console)/page.tsx:92-96  ℹ️  P3: Caching gap — no `unstable_cache` / `revalidate`

    statically cache it and every load re-executes the full fan-out. Query budget per `/admin`

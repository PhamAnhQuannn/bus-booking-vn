## Direct answer: is error capture actually live in production?

**Partially, and much less than the code reads as.**

1. **The DSN.** `SENTRY_DSN` and `NEXT_PUBLIC_SENTRY_DSN` are **commented out in
   `.env.example:172-173`, and absent from `.env.local`, `.env.production.local`,
   `.env.production.example`, and `.env.staging.example`.** I cannot read the Vercel
   project's environment from this working tree, so I **cannot confirm** whether prod has
   a DSN set. Every on-disk signal says unset. **This needs a human to check the Vercel
   dashboard — do not treat it as answered.**

2. **If the DSN is unset**, `captureException` falls back to `logger.error(..., sentry:'fallback')`
   (lib/observability/sentry.ts:157) and `instrumentation.ts` never calls `Sentry.init` at
   all. Every error lands in Vercel stdout logs. Nothing alerts. That is a *working* sink,
   just not a monitored one.

3. **If the DSN is set**, capture is still far narrower than it looks:
   - **Server**: only the **4 explicit `captureException` call sites** in the whole
     repo reach Sentry — `app/api/payments/bank_transfer/webhook/route.ts:81`,
     `lib/jobs/processPayouts.ts:198`, `lib/notification/dispatchNotifications.ts:232`,
     `lib/payment/processWebhook.ts:133,465`. Uncaught errors in **route handlers,
     Server Components, server actions, and the Edge proxy** do **not** reach Sentry —
     see P1-1.
   - **Client**: the browser SDK initialises but its egress is **blocked by this app's
     own CSP** for any regionally-issued DSN — see P1-3. And React render errors are
     `console.error`'d, never captured — see P1-2.

**Net: with a DSN set, Sentry would receive four hand-placed server events and, for the
browser, likely nothing at all.**

# P1 — BLOCKING (for go-live wiring, not for these merges)

### P1-1 · `instrumentation.ts:15-35` 🔇 No `onRequestError` — server errors never reach Sentry

`instrumentation.ts` exports only `register()`. It does **not** export:

```ts
export const onRequestError = Sentry.captureRequestError;
```

Next.js catches errors thrown inside route handlers, Server Components, server actions
and middleware, converts them to a 500 + `digest`, and **never lets them reach the
process-level `uncaughtException` / `unhandledRejection` handlers** that Sentry's default
integrations hook. `onRequestError` is the *only* mechanism by which those errors reach
the SDK. Sentry's Next.js manual-setup guide states this export is what "capture[s]
errors from Server Components, middleware, and proxies."

Consequence: every 500 this app serves from an unhandled throw is invisible to Sentry.
Only the four hand-placed `captureException` calls get through. The user-facing side of
this is the `Mã lỗi: {digest}` shown in `app/error.tsx:32` — a correlation id pointing at
a record that was never created.

**Fix:** add the export to `instrumentation.ts` in the same commit as any DSN wiring.

### P1-2 · `app/global-error.tsx:18`, `app/error.tsx:21` 🔇 Error boundaries `console.error` only

```ts
useEffect(() => {
  console.error(error);   // app/error.tsx:21 and app/global-error.tsx:18
}, [error]);
```

`app/error.tsx:23`'s own comment says *"Surface to the console/monitoring"* — but there is
no monitoring call. `console.error` in a browser is not telemetry; nothing collects it.
`global-error.tsx` is the last-resort root boundary — the single highest-value client
error surface in the app — and it reports nowhere. Sentry's Next.js guide requires
`Sentry.captureException(error)` in exactly this hook.

Combined with P1-1 this closes the loop: a Server Component throws → not captured
server-side (P1-1) → the client boundary that receives it `console.error`s (P1-2) → the
event exists in no system.

**Fix:** `Sentry.captureException(error)` inside the `useEffect` in both files. Note both
are `'use client'` — import `@sentry/nextjs` directly, **not** `@/lib/observability`
(that barrel reaches `lib/logger` + `lib/config`; see the 2026-06-04 operator-smoke entry
in CLAUDE.md).

### P1-3 · `next.config.ts:19` 🚧 CSP `connect-src` cannot match a regional Sentry ingest host

```ts
`connect-src 'self'${hasSentry ? ' https://*.ingest.sentry.io' : ''}...`
```

Sentry has issued **regional** ingest hostnames for years: `o<orgId>.ingest.**us**.sentry.io`
/ `…ingest.**de**.sentry.io`. This repo's own setup guide already documents the regional
form:

> `documentation/guides/07-setup-sentry.md:98`
> `SENTRY_DSN="https://abc123@o123456.ingest.us.sentry.io/789012"`

`o123456.ingest.us.sentry.io` does **not** end with `.ingest.sentry.io` — the suffix is
`.us.sentry.io`. The pattern fails under the permissive multi-label reading of the CSP
host wildcard *and* under the stricter single-label reading that Sentry themselves
document as a real-world gotcha ([sentry-docs#17202](https://github.com/getsentry/sentry-docs/issues/17202)).
Browser transport is `fetch`/`sendBeacon`, both governed by `connect-src`.

This is the shape flagged in CLAUDE.md 2026-07-26: *a guard whose failure is suppressed by
the very state that makes it inert.* `hasSentry` is false today, so the directive is not
even emitted and nothing is broken. It **arms on the exact next action** — setting
`NEXT_PUBLIC_SENTRY_DSN` — and then fails **silently**: no console error visible to the
operator wiring it up, no events in Sentry, and the natural conclusion is "Sentry is
broken" rather than "our CSP blocks it."

**Fix:** widen to cover the regional hosts, e.g.
`https://*.ingest.sentry.io https://*.ingest.us.sentry.io https://*.ingest.de.sentry.io`,
or derive the origin from the DSN at config time (`new URL(dsn).origin`) so the two can
never drift. Verify with a real event before declaring the DSN wiring done.

# P2 — SHOULD FIX

### P2-4 · `next.config.ts:30-53` 📦 No `withSentryConfig` — arriving events would be unreadable

The Next SDK's build wrapper is absent entirely. Consequences: **no source-map upload**
(every stack frame minified — the 10.66/10.67 `in_app` frame-classification fixes that
#384 delivers are unusable without it), no release/dist tagging (no regression attribution,
no "first seen in" ), no build-time route wrapping, no tunnel option (which is also the
standard workaround for P1-3). `instrumentation-client.ts` is still auto-loaded — Next
supports that natively since 15.3 — so the client SDK does init; it just produces
unattributable output.

### P2-5 · `lib/config/env.ts:277` + `instrumentation-client.ts:74` 🔇 `NEXT_PUBLIC_SENTRY_DSN` bypasses the Zod schema

The schema declares `SENTRY_DSN: z.string().optional()` and **nothing for
`NEXT_PUBLIC_SENTRY_DSN`**, which `instrumentation-client.ts:74` reads straight off
`process.env`. So the client DSN gets no boot-time validation, no shape check, no
production `superRefine`. A typo, a missing `NEXT_PUBLIC_` prefix, or a var set in the
wrong Vercel environment produces `dsn === undefined` → `if (dsn)` false → **the browser
SDK silently never initialises**, indistinguishable from "no errors happened." Same class
as the missing-CI-env entry (CLAUDE.md 2026-06-21): a var outside the centralised schema
fails silently rather than at boot.

### P2-6 · `instrumentation.ts:16` vs `lib/observability/sentry.ts:141,147-153` ⚠️ `sentry:'forward'` can assert a forward that did not happen

Two different files decide "is Sentry on" from two different sources under two different
conditions:

- `instrumentation.ts:16` — inits **only** when `process.env.SENTRY_DSN` **and**
  `NEXT_RUNTIME === 'nodejs'`.
- `lib/observability/sentry.ts:141` — branches on `getEnv().SENTRY_DSN` **with no runtime
  check**, then calls `Sentry.captureException(...)` and logs `sentry: 'forward'`,
  **returning early** so the fallback sink is skipped.

On any Edge-runtime path (the proxy, any `export const runtime = 'edge'` route) with
`SENTRY_DSN` set, `Sentry.captureException` runs against an uninitialised client — a
no-op — while the log line claims `sentry:'forward'`. The event reaches **neither** sink,
and the log asserts that it reached one. This is the "an invariant comment asserting
something its own conditions contradict" family (CLAUDE.md 2026-07-28): a log field is a
claim about what happened, and emitting it unconditionally makes the claim false.

**Fix:** gate the forward branch on the SDK actually being initialised
(`Sentry.getClient() !== undefined`) rather than on the env var, and fall through to the
logger sink when it is not.

### P2-7 · 13 cron routes ⚠️ Job failures log but never reach the error sink

Every cron route follows the same shape —
`app/api/cron/reconcile-payments/route.ts:45-46`,
`app/api/cron/process-payouts/route.ts:32-33`, and 11 siblings:

```ts
} catch (err) {
  logger.error({ err }, 'reconcile-payments: cron run failed');
  return NextResponse.json({ error: 'internal_error' }, { status: 500 });
}
```

Correct per skill Cat 3 (a structured log is present, not swallowed, not `console`). But
`captureException` is **not** called, and P1-1 means the 500 does not reach Sentry either.
So a **totally failing** `reconcile-payments` — the sweeper that is the safety net behind
the whole bank-transfer money path — produces a pino line in Vercel stdout and nothing
else. No alert, no aggregation, no "this has failed 40 consecutive ticks" signal. The
money paths are precisely where this project's history says silent failure costs real
outcomes.

**Fix:** `captureException(err, { area: 'cron.<job>' })` alongside the existing
`logger.error` in each cron catch. The seam already degrades to the logger when no DSN is
set, so this is safe to land before the DSN exists.

### P2-8 · `lib/jobs/reconcilePayments.ts:710` 📊 Starved vs. idle is **still** indistinguishable

The 2026-07-24 CLAUDE.md entry is **still accurate as written**. The file's own docblock
restates the problem as live:

> `lib/jobs/reconcilePayments.ts:100-104`
> "the candidate query is `ORDER BY createdAt ASC LIMIT CLAIM_LIMIT`, and held rows are
> the oldest, so they consume the whole budget and the sweeper stops reaching newer
> bookings…; `rowsAffected` counts only paid+expired, so a fully starved tick reports
> success with 0 and looks exactly like an idle healthy one"

What **did** land is a *correctness* bound — `SUSPECTED_HOLD_MAX_AGE_MINUTES = 24h`
(`:115`) caps how long a hold can starve the budget. That fixes the outage. It does not
fix the **observability**: the return is still

```ts
return { rowsAffected: paidCount + expiredCount, status: 'success' };   // :710
```

with no candidate count and no saturation flag. `candidates.length === CLAIM_LIMIT`
(`:302-334`) is the exact discriminator between "nothing to do" and "budget exhausted,
backlog growing" and it is **never emitted anywhere** — not in the return, not in a log,
not in the `JobRunLog` row.

Per-event logging in this file is genuinely good — `reconcile.unmatched_payment_suspected`
(`:599`), `reconcile.unmatched_payment_unresolved` (`:615`),
`reconcile.event_unrecoverable` (`:699`), `reconcile.booking_expired` (`:688`) — so an
operator reading logs can reconstruct what happened. But nothing tells them the sweeper
**stopped reaching rows**, which is the failure that hides.

**Fix (cheap, one line):** include `candidateCount` and `saturated: candidates.length === CLAIM_LIMIT`
in the tick's summary log and in the returned result. `processPayouts` already
demonstrates the pattern — see below.

### P2-9 · `proxy.ts:175-188` + 2 call sites 🔗 ADR-007's compensating control is ~2% deployed

ADR-007 accepted "no tracing" **in exchange for** "request-scoped `correlationId` to all
log entries, enabling grep-based trace reconstruction" (`:217`). The header half shipped —
`proxy.ts:175-188` mints/propagates `x-request-id` onto both forwarded request and
response headers. The logging half essentially did not:

    lib/observability/requestId.ts:37  loggerForRequest(rid)
      consumers:
        app/api/holds/route.ts:44
        app/api/cron/sweep-holds/route.ts:25
      ...that is the complete list.

Every other route, and every money path — `reconcilePayments`, `processPayouts`,
`processWebhook`, the bank-transfer webhook — imports the bare module-level `logger`. **No
log line on any money path carries a `requestId`.** Grep-based trace reconstruction, the
thing traded away tracing for, does not work for the flows that most need it.

Mitigating (worth stating): the money paths do log `bookingRef` / `paymentEventId` /
`providerTxnId`, which are serviceable correlation keys for a support agent chasing one
booking. What is missing is request-level correlation across the handler chain. Cron jobs
would need a `jobRunId` rather than a request id.

`requestId.ts:15-17` itself flags the remaining work as deferred ("thread the id
implicitly through AsyncLocalStorage"). That deferral is now ~2 months old and the ADR
depends on it.

### P2-10 · `lib/jobs/runJob.ts:41-50` ⚠️ The failure record is written by the operation most likely to be failing

```ts
} catch (err) {
  const errorMessage = err instanceof Error ? err.message : String(err);
  await prisma.jobRunLog.create({ /* status: 'failed', errorMessage */ });   // :41
  throw err;
}
```

The **only** durable record of a job failure is a **database write**. If the job threw
because the DB was unreachable, pool-exhausted, or mid-failover — a leading cause of job
failure, and the exact scenario the `DATABASE_POOL_MAX=1` work in #382 was about — this
`create` throws too, **replaces** the original error, and the `JobRunLog` row is never
written. The catch also emits **no log of its own**; it relies entirely on the caller's
`logger.error`, which does fire (P2-7) but with the *substituted* Prisma error, not the
original cause.

**Fix:** `logger.error({ err }, 'runJob.failed')` **before** the `create`, and wrap the
`create` in its own try/catch so a bookkeeping failure cannot mask the real one.

# P3 — ADVISORY

### P3-11 · `instrumentation.ts:23`, `instrumentation-client.ts:80` 📊 `tracesSampleRate: 0` does not disable tracing

Verified against the installed SDK —
`node_modules/.pnpm/@sentry+core@10.65.0/…/utils/hasSpansEnabled.js:5-12`:

```js
function hasSpansEnabled(maybeOptions) {
  if (typeof __SENTRY_TRACING__ === "boolean" && !__SENTRY_TRACING__) return false;
  const options = maybeOptions || getClient()?.getOptions();
  return !!options &&
    // Note: This check is `!= null`, meaning "nullish". `0` is not "nullish"…
    (options.tracesSampleRate != null || !!options.tracesSampler);
}
```

`0 != null` → **`true`**. Tracing is **enabled at 0% sampling**, not disabled. So:

- the full OpenTelemetry + orchestrion instrumentation stack loads and runs on every
  server request — spans are constructed, then dropped at the sampling gate. Cold-start
  and per-request CPU cost, zero data value.
- `sentry-trace` / `baggage` headers are still attached to outbound requests (SePay,
  VietQR, Upstash, …).
- **this is precisely where all of #384's real delta lands**: OTel 2.9→2.10 and
  `@apm-js-collab/{tracing-hooks, code-transformer, bundler-plugins}`. #384 upgrades, in
  full, the machinery whose every output this app throws away. That is the cleanest
  possible statement of why the bump is hygiene rather than capability.

**Fix, if the intent is "off":** omit `tracesSampleRate` entirely, or set
`__SENTRY_TRACING__: false` via the bundler define. If the intent is "keep the plumbing
warm for the Phase-3 Tempo migration ADR-007 anticipates", say so in a comment at both
init sites — right now nothing distinguishes the two intents, which is what made this
question necessary at all.

## What is currently unobservable

Ranked by "how much would it cost us to not know."

1. **Any uncaught server error.** Route handlers, Server Components, server actions, Edge
   proxy. Not in Sentry (P1-1); reaches Vercel stdout only if some enclosing handler logs
   it. The `digest` shown to the user (`app/error.tsx:32`) points at nothing. **Highest-value
   single fix in this document: one exported line in `instrumentation.ts`.**
2. **Any client-side error.** Render errors are `console.error`'d only (P1-2), and even a
   correctly-captured event cannot egress under the current CSP for a regional DSN (P1-3).
   The browser is effectively a black box.
3. **Cron job health.** 13 scheduled jobs. A failing tick writes a `JobRunLog` row and one
   pino line; nothing alerts on either (P2-7), and if the DB is the thing failing, not even
   the row (P2-10). "reconcile-payments has failed every tick for six hours" is not a
   question any system here can answer.
4. **`reconcilePayments` budget saturation** (P2-8). Still literally indistinguishable from
   idle, as documented in the file's own comment. One counter fixes it; `processPayouts`
   already shows how.
5. **Request-level correlation on the money paths** (P2-9). ADR-007 traded tracing away for
   this and it was never built out past two routes.
6. **Anything requiring a rate, a trend, or a threshold.** There is no metrics system at
   all — no counters, no histograms, no gauges. Every question of the form "how often",
   "how long", "is this getting worse" is unanswerable without ad-hoc SQL against
   `JobRunLog` / `PaymentEvent`. This is a defensible Phase-1 posture given ADR-007, but it
   should be a known one: **the only alerting-capable sink this application has is Sentry,
   and Sentry currently receives four hand-placed event types.**

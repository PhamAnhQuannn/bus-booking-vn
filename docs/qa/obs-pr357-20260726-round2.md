## P1 — BLOCKING

### `lib/jobs/reconcilePayments.ts:389-403` 🔇 P1: the new signal is gated on `linked`, so the **orphan** half — Bug B's actual shape on the live rail — is still silent

Round 1's P1 was *"an unreadable payment is indistinguishable from no payment."* `0f43bfb`
adds `reconcile.event_unrecoverable` — but scoped to linked events only:

```ts
if (!confirming && linked.length > 0) {
  for (const e of linked) {                       // ← linked ONLY
    if (e.amount === 0 && !e.success) { logger.warn(…); }
  }
}
```

`events` (`:368`) contains **both** linked events *and* orphans (`pe."bookingId" IS NULL`,
`:355-365`), and orphans are the input to `matchDegraded`. An orphan whose stored body cannot
be parsed is rejected at `matchDegraded`'s `if (!ev.success || …) continue;` (`:271`) and then
falls straight through to the expiry branch — **emitting nothing at all**. Identical
before and after this commit.

That is not the minor half. The Bug B / SePay money-loss scenario recorded in CLAUDE.md is
*specifically* the orphan path — *"a VN bank memo the customer never typed or the bank mangled
past recognition"* → `bookingId NULL` → degraded match. `bank_transfer` is the **live rail
today**; VNPay is behind `VNPAY_ENABLED`. So the fix instruments the half that is currently
dark and leaves dark the half that is currently live.

Concretely: if `recoverSepayEvent` ever regresses the way `recoverEvent` did, a real transfer
lands as an orphan, parses to `{0,false}`, is silently skipped by `matchDegraded`, and the
booking is terminally expired — with `reconcile.booking_expired` as the only log line, exactly
as in the original Bug B. The stated purpose of this instrumentation is to make that
detectable, and for orphans it does not.

**Fix:** iterate `events`, not `linked`, and include `bookingId: e.bookingId` (null ⇒ orphan)
so the two cases are distinguishable in the log:

```ts
for (const e of events) {
  if (e.amount === 0 && !e.success) {
    logger.warn({ bookingId: booking.id, eventBookingId: e.bookingId, … }, 'reconcile.event_unrecoverable');
  }
}
```

Note this makes the noise problem in P2-2 worse, so land it together with a
discriminating predicate (P2-1).

## P2 — SHOULD FIX

### P2-1 `lib/jobs/reconcilePayments.ts:161, 397` ⚠️ `bodyShape` cannot discriminate the two cases it was added to separate

The comment (`:387-388`) and the PR body both state that `shape` *"is what tells an operator
'parser mismatch' apart from 'customer's payment failed'."* On the VNPay rail — the rail this
PR exists for — it does not:

| Case (adapter `vnpay`) | recovered | `shape` |
|---|---|---|
| declined payment, genuine urlencoded body | `{0,false}` | `non-json` |
| unreadable / format-mismatched body | `{0,false}` | `non-json` |

Identical on both axes. `bodyShape` only varies when a row's format is *unexpected for its
adapter* — and after this fix no such row exists, because routing is now shape-driven. The
field is a tautology with respect to the routing decision it purports to explain.

**Round 1 predicted this exactly** (P3 #1): *"`recoverVnpayEvent` collapses four distinct
outcomes … into one indistinguishable `{0,false}` … The recovery twin returning a bare tuple
is what forces P1's fix to live awkwardly at the call site."* The fix landed at the call site
anyway, and inherited the flaw.

**Fix:** put the discriminator in the parsers, where the information exists. Return
`{ amount, success, reason }` mirroring the file's own `VerifyWebhookResult` convention
(`'parse_failed' | 'unknown_status' | 'pending' | 'declined' | 'zero_amount'`) and log
`reason`. `verifyWebhook` in the same adapter already does precisely this with its
`missing_signature` / `sig_mismatch` / `invalid_amount` discriminator — the recovery twin
should match its sibling.

### P2-2 `lib/jobs/reconcilePayments.ts:389-403` ⚠️ warn-level noise on a normal condition, with no termination bound

Two separate problems in one loop:

1. **Fires on ordinary declines.** A legitimately declined payment yields `{0,false}`, so
   `reconcile.event_unrecoverable` — a *warn* with "parser/format mismatch" in the message —
   fires for every customer whose card was refused. Warn-level is reserved for "something is
   wrong with the system"; this is "something is normal about the customer."
2. **Repeats forever.** A booking with `holdExpiresAt === null` never reaches the expire
   branch (`:605-611`, `if (!holdExpired) continue;`), so it stays in the candidate set
   indefinitely and re-emits this warn **every 15-minute tick, in perpetuity** — ~96 lines/day
   per such booking, permanently. Structurally the CLAUDE.md 2026-07-24 "Bug B round 3"
   pattern (*a skip that keeps a row in a bounded work-queue's candidate set without changing
   anything the next iteration reads*), manifesting here as unbounded log volume instead of
   budget starvation.

Combined effect: the signal added to make a rare defect visible will be buried under routine
declines, which is how it fails to do its job. Alert fatigue on a warn stream is the same
outcome as no signal.

**Fix:** gate on `reason === 'parse_failed'` (P2-1) rather than on `{0,false}`, and aggregate
to one line per booking per tick rather than one per event.

### P2-3 `lib/jobs/reconcilePayments.ts` (whole file) ⚠️ still no Sentry escalation — round-1 P2, still open, and **not disclosed** in the PR body

Round 1: *"Money-path failures in this job are never escalated to Sentry, unlike every
sibling."* Unchanged at `0f43bfb` — `reconcilePayments.ts` still has no
`import { captureException } from '@/lib/observability'`, while `lib/jobs/processPayouts.ts:133`
and `lib/payment/processWebhook.ts` both use it.

The new `event_unrecoverable` warn makes this more pointed, not less: a **linked**
unreadable payment event is a code defect (the row was verified at ingest, so it must be
parseable), not an operational condition. It belongs in the exception stream, not only in a
warn line that nobody greps. Note this only holds once P2-1 lands — today the warn cannot tell
a defect from a decline, so escalating it as-is would page on refused cards.

Unlike the three findings the PR body carries in "Not delivered", this one was dropped
silently.

### P2-4 `runJob.ts` / `JobRunLog` ⚠️ still no tick-level summary — round-1 P2, still open (correctly disclosed)

`rowsAffected` sums paid + expired, so a tick in which an entire rail is dark is byte-identical
to an idle tick. The PR body discloses this in "Not delivered" and scopes it to #143, which is
the right handling — recorded here only so it is not lost between rounds.

Worth noting the interaction: this is the *reason* P1 matters. With no tick summary, a
silently-skipped orphan produces no aggregate anomaly either — the two blind spots compose
into total invisibility, which is exactly how Bug B survived for its whole life.

PRIORITY 1 — Block merge, fix first:

  [SCOPE / CLAIMED CLOSURE] PR body line 1 — "Closes #337"
    Merging auto-closes #337, and on squash-merge this body becomes the permanent master commit
    message. But the shipped gate is `!NOTIFY_STUB && EMAIL_PROVIDER !== 'resend'`, and:
      - `NOTIFY_STUB` schema default is `'true'` (lib/config/env.ts:157-160),
      - `.env.production.local` sets `NOTIFY_STUB="true"`,
      - FI-014 Known Gaps (this PR's own file) still lists eSMS brandname registration as an
        unstarted 2-4 week HIGH blocker, so `NOTIFY_STUB=false` is not reachable near-term.
    So in the only environment that exists, the warn never evaluates — including for the
    configuration that would actually silence customer email here (`NOTIFY_STUB=true` +
    `EMAIL_PROVIDER` missing). The PR closes the issue and the master history will record it as
    handled, while the harm described in #337 stays undetectable in production.

    This is the PR-shape face of code-review P1 #1. Fix either:
      (a) widen the gate to `EMAIL_PROVIDER !== 'resend'` alone (preferred — #326 decoupled the
          two flags and this re-couples them), or
      (b) downgrade to `Refs #337` and state the residual gap explicitly in the body, so the
          permanent commit message does not overclaim.

  [NEGATIVE SPACE / .env.example not updated]
    This PR's stated deliverable is "Docs updated to the two-flag reality". `.env.example` — the

    to kill. DS-006 and FI-014 were corrected; the one operator-facing template was not.
    Fix: update both comment blocks in this PR.

    `EMAIL_FROM="noreply@busbookvn.com"` while the schema default and prod both use
    `noreply@lenxevn.com`.)

  [PR BODY / RATIONALE THAT BECOMES PERMANENT HISTORY]
    Body: "not a hard error, since SMS-only deployments are legitimate."
    This repo has no SMS-only deployment and no SMS at all: prod is `NOTIFY_STUB="true"` +
    `EMAIL_PROVIDER="resend"` — email-only. The severity decision (warn, not fail) is justified
    in the body by a deployment topology that is the inverse of the real one, and squash-merge
    makes that justification permanent guidance for whoever revisits this next.
    Mistake Log, 2026-07-24: "before squash-merging, re-read the PR body against the FINAL diff"
    and "state the rationale in terms of what the OTHER configuration does", not the hypothetical.
    Fix: restate the rationale against the actual prod topology, or change the severity
    (see code-review P2 "warn vs hard fail", which carries a WT-20(b) ci.yml obligation).

  [TEST PLAN DOES NOT COVER THE HEADLINE CLAIM]
    "## Verify — `pnpm test`" lists three unit assertions, all of which call `getEnv()` directly.
    The PR's headline claim — in the title, body, code comment, DS-006 and FI-014 — is *boot*
    behavior. Nothing calls `getEnv()` at server start: `instrumentation.ts register()`
    initializes Sentry only. So the warn actually fires on the first request that reads env in
    each serverless instance, once per cold start, into request logs — not at deploy. No item in
    the test plan or the diff demonstrates a boot-time emission.
    Fix: add a `getEnv()` call to `instrumentation.register()` (which would also make the file's
    own header claim at env.ts:4 — "Parsed once at module-load time so misconfigured deploys fail
    fast" — true), or drop "boot" from the title/body/docs and describe the real trigger point.

  [DOC SHAPE / FI-014 Known Gaps]

    "**HIGH -- NOTIFY_STUB default in production**" bullet, growing it to ~4 lines. FI-014 Known

    Fix: add a sibling HIGH bullet for `EMAIL_PROVIDER` rather than a sub-clause.

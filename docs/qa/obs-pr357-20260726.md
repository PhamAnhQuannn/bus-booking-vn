P1 — BLOCKING:

  lib/jobs/reconcilePayments.ts:193-196  🔇 P1: New money-path failure mode is completely silent — an unreadable payment is indistinguishable from no payment.

    `recoverVnpayEvent` returns `{ amount: 0, success: false }` for **every** body it cannot
    make sense of: a stub-produced JSON body (see the P1 in `code-review-pr357`), a truncated
    row, an unrecognised `vnp_TransactionStatus`, any future VNPay format change. It never
    throws and — because the new branch sits *outside* the `else`'s `try/catch` — there is not
    even a catch site where a log could have gone. Nothing is emitted.

    Downstream, that `{0,false}` makes `isConfirming` false, and the booking falls through to
    the expiry branch, which logs `logger.info({ bookingRef, suspectedUnresolved }, 'reconcile.booking_expired')`
    (line 602). Those fields are **identical** whether the booking had no `PaymentEvent` at all
    or had one carrying a successful payment the sweeper could not parse. Oncall has no signal
    separating "customer never paid" from "we stored their payment and then failed to read it,
    and drove the booking to a TERMINAL state."

    This is not hypothetical — it is the precise mechanism that hid Bug B. The 2026-07-23 entry
    records that every `bank_transfer` event recovered as `{0,false}` and *nothing surfaced it*
    until bookings were already terminally expired with money in the account. This PR fixes the
    parse for one rail while faithfully reproducing the silence for the next failure on it. And
    it is not dormant: the stub-vnpay regression identified in `code-review-pr357-20260726.md`
    would ship and run in production emitting **exactly zero** distinguishing telemetry.

    Fix (one line, in `recoverEvent` right after the adapter-specific call):
      `if (!success) logger.warn({ paymentEventId: row.id, adapter: row.adapter, providerTxnId: row.providerTxnId }, 'reconcile.event_unrecoverable — stored payment event could not be confirmed');`
    A stored `PaymentEvent` that the sweeper cannot turn into a confirmation is always worth a
    warn: the row exists only because a webhook was accepted, so "we accepted it and now cannot
    read it" is by definition anomalous. This converts every future instance of this class —
    for every adapter, including ones not yet written — from invisible to greppable.
    (Note `logger` is already in scope at that point only inside the exported job; `recoverEvent`
    is a module-scope helper, so either pass the logger in alongside the recoverers or move the
    check to the call site at line 338.)

P2 — SHOULD FIX:

  lib/jobs/reconcilePayments.ts:609 (+ runJob.ts:29-37)  ⚠️  P2: No tick-level summary — a mis-parsing sweep is indistinguishable from an idle one.

    The job emits per-booking logs and then returns `{ rowsAffected: paidCount + expiredCount,
    status: 'success' }`. There is **no tick summary log at all**: a tick that claimed 200
    candidates and resolved none writes nothing beyond a `JobRunLog` row reading
    `{ status: 'success', rowsAffected: 0 }` — byte-identical to a healthy idle tick.

    The file's own header already names this hazard for the starvation case
    (lines 103-105: "`rowsAffected` counts only paid+expired, so a fully starved tick reports
    success with 0 and looks exactly like an idle healthy one"). This PR adds a *second* route
    to that same indistinguishable state — unparseable events produce neither a paid nor a
    signalled expiry — without adding the breakdown the comment implies is missing. `rowsAffected`
    also sums two very different outcomes, so even a non-zero value hides a rail going dark
    (e.g. paid 0 / expired 12 reads the same as paid 12 / expired 0).

    Fix: emit one `logger.info({ candidates: candidates.length, paidCount, expiredCount, heldCount, unrecoverableCount }, 'reconcile.tick')` before the return. That single line makes
    starvation, rail-dark, and parse-failure all visible without a per-booking grep, and gives
    the `JobRunLog` row something to be correlated against.

  lib/jobs/reconcilePayments.ts (whole file)  ⚠️  P2: Money-path failures in this job are never escalated to Sentry, unlike every sibling.

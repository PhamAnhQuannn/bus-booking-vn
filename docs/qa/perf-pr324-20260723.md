## P1 — BLOCKING

### `lib/jobs/reconcilePayments.ts:258-281` 🐢 P1: per-candidate orphan-window query has an unindexed range predicate; the OR-branch went live in this PR

```sql
WHERE pe."bookingId" = $1::uuid
   OR ( pe."bookingId" IS NULL
        AND pe."receivedAt" >= $2 AND pe."receivedAt" <= $3 )
```

This runs **once per candidate booking** inside `for (const booking of candidates)`,
bounded by `CLAIM_LIMIT = 200`, all inside the single advisory-locked transaction.
By the skill's own detection rule this is a textbook N+1 (`await tx.$queryRaw` inside
an added-scope loop) — but the loop and the query are pre-existing, so the *new* fact
is that the second OR-branch stopped being provably empty.

**Before this PR** `PaymentEvent.bookingId` was `NOT NULL`, so `bookingId IS NULL`
matched zero rows by construction. The planner still had to *plan* it, but the branch
cost nothing at execution. **After the migration** it is a live predicate over a
growing set with no supporting index on the only selective column in it.

**Does the btree on `bookingId` serve `IS NULL`?** Yes. Postgres btrees index NULLs
and `IS NULL` has been an indexable qual since 8.3, so the planner's best shape here
is a `BitmapOr` of two bitmap index scans on `PaymentEvent_bookingId_idx`
(`bookingId = $1` and `bookingId IS NULL`) followed by a bitmap heap scan. **But the
`receivedAt` range cannot participate** — it is applied as a heap recheck *after*
every orphan row has been fetched. So the branch's cost is `O(total_orphans)` heap
fetches per candidate, regardless of how narrow the ±30-minute window is.

Two degradation modes, in order of arrival:

1. **Bitmap-heap growth (gradual).** Cost per tick ≈ `candidates × orphan_pages`.
2. **Planner flip to seq scan (cliff).** The `bookingId IS NULL` bitmap estimate comes
   straight from `pg_statistic.null_frac`. Once orphans are roughly **>5–10 % of
   `PaymentEvent` rows**, the estimated bitmap heap pages exceed the seq-scan
   crossover and Postgres abandons the index for the whole OR. At that point every
   candidate does a full-table scan of a `TEXT`-heavy table.

**Sizing.** A `PaymentEvent` row is ~550–800 B (a SePay body is ~400–700 B of `rawBody`
`TEXT`, stored inline — under the 2 KB TOAST threshold), so ~10–14 rows/8 KB page.

| Unclaimed orphans | Orphan pages | Per candidate (warm) | ×200 candidates |
|---|---|---|---|
| 100 | ~10 | < 1 ms | ~0.1 s |
| 2,000 | ~170 | ~2–4 ms | ~0.5 s |
| 20,000 | ~1,700 | ~15–30 ms | **3–6 s** |
| 100,000 | ~8,500 | ~80–150 ms warm / ~0.8 s cold | **16–30 s warm, minutes cold** |

The cron route (`app/api/cron/reconcile-payments/route.ts`) declares no
`maxDuration`, so the tick inherits the Vercel platform default. Once the tick can no
longer finish, the function is killed mid-transaction — the advisory lock is released
by the aborted tx, but nothing is reconciled, and the same 200 oldest candidates are
re-attempted on the next tick with the same result. The sweeper wedges *silently*.

**Challenging the design review's rejection of the partial index.** The rejection rests
on "orphan volume is tiny at launch scale". That is true of *booking-derived* orphans —
but orphan creation is not gated on bookings at all. `app/api/payments/bank_transfer/webhook/route.ts`
now writes an orphan for **every inbound credit whose memo has no parseable ref**, and
SePay fires the webhook on **every credit to the receiving account**, not only on
booking payments. Per `lib/payment/adapters/bankTransfer.ts:84-100` the only gates
before `unmatched` is populated are `transferType === 'in'` and `transferAmount > 0`.
So orphan volume is coupled to *total bank-account activity*, and per
`memory/business-initial-operators.md` this is a family operator's **single shared bank
account**. Any personal or non-platform credit to it becomes a permanent orphan row.
Nothing in the PR deletes orphans — the schema comment explicitly forbids it
("never delete one without reconciling it against the bank statement first").

At 20 unrelated credits/day → 7,300 orphans/yr (comfortably into the "watch" band in
~3 months). At 100/day → the 20,000 row band in ~7 months and the planner-flip
threshold well inside 2 years. This is not a launch-scale problem, but it is a
*this-decade, no-alarm-will-fire* problem on a payment-recovery path.

**Repo-rule check.** CLAUDE.md: *"Cron/sweeper WHERE predicates MUST be top-level
indexed columns, never JSON-payload keys."* `receivedAt` satisfies the letter
(top-level column, not a JSON key) but not the intent — the rule exists to prevent
exactly this seq-scan-over-time shape, and the audit step it prescribes greps only for
`payload->>`. `bookingId IS NULL` **is** indexed, so the rule is half-satisfied. Call
it a violation of intent, documented rather than hidden.

**Fix** (one migration line, SQL-only, ~16 B/entry — a few hundred KB even at 20k orphans):

```sql
-- Partial index: only orphan rows are indexed, so it stays tiny and shrinks
-- as the sweeper claims rows. Prisma DSL cannot model a WHERE-clause index,
-- so this stays SQL-only per CLAUDE.md ("Partial/WHERE indices stay SQL-only").
CREATE INDEX "PaymentEvent_orphan_receivedAt_idx"
  ON "PaymentEvent" ("receivedAt")
  WHERE "bookingId" IS NULL;
```

Plain `CREATE INDEX` (not `CONCURRENTLY`) is correct here: Prisma runs each migration
file in a transaction and `CONCURRENTLY` is illegal inside one, and the table is small
enough today that the `SHARE` lock is milliseconds. Do it now, while that is true.

Secondary narrowing worth folding in (see P3-2): scope the orphan branch to
`pe."adapter" = 'bank_transfer'`, since no other adapter can produce an orphan.

## P2 — SHOULD FIX

### `lib/payment/processWebhook.ts:232` ⚠️ P2: new ABBA lock ordering between the webhook tx and the reconcile sweeper tx

This is the second-order effect of the added `updateMany`, and it is a genuinely new
hazard — not merely an extra statement.

**Does the UPDATE take locks the old code did not?** Yes, and specifically a lock on a
*pre-existing* row. `tx.paymentEvent.create(...)` only took a speculative unique-index
insertion lock on a key nobody else held; it could not block on an existing row. The
new `updateMany({ where: { adapter, providerTxnId, bookingId: null } })` takes a
row-level exclusive (`FOR UPDATE`-strength) lock on the matched `PaymentEvent` row.

**Does it lock a row belonging to another booking?** No — and this part is sound. The
`(adapter, providerTxnId)` equality is the *full* unique key, so the index scan yields
at most one row, and the `bookingId IS NULL` qual is then evaluated. A row that fails
that qual is filtered *before* being locked, so an already-linked event belonging to
another booking is never locked. The claim can only ever touch an orphan.

**The ordering problem.** Comparing the two transactions:

| | Webhook tx (`processWebhook.ts`) | Sweeper tx (`reconcilePayments.ts`) |
|---|---|---|
| 1 | `UPDATE PaymentEvent` (claim orphan) — **:232** | `pg_advisory_xact_lock` |
| 2 | `UPDATE Booking` (`applyPaidTransition.ts:70`) | `SELECT … FOR NO KEY UPDATE OF b SKIP LOCKED` on **up to 200 Booking rows** — **:219-249** |
| 3 | `SELECT Trip … FOR UPDATE` | `UPDATE PaymentEvent` (CAS claim) — **:311-316** |
| 4 | — | `UPDATE Booking` |

Webhook acquires **PaymentEvent → Booking**. Sweeper acquires **Booking → PaymentEvent**.
Classic ABBA. Concrete interleaving:

1. Sweeper claims booking `X` (and 199 others) with `FOR NO KEY UPDATE`, holds them for
   the whole tick.
2. SePay redelivers the transfer for `X`; the webhook tx claims the orphan row `O` at
   step 1 and locks it.
3. Webhook proceeds to `UPDATE Booking WHERE id = X` → blocks (a plain `UPDATE`
   requires `FOR NO KEY UPDATE` strength, which conflicts with the sweeper's).
4. Sweeper's loop reaches `X`, degrade-matches `O`, issues the CAS `UPDATE` on `O` →
   blocks on the webhook.
5. Deadlock. Postgres kills one after `deadlock_timeout` (1 s default).

The advisory lock does **not** protect against this — it serializes ticks against each
other, not against webhooks. `SKIP LOCKED` also doesn't help: it only saves the sweeper
when the webhook took the Booking lock *first*, which is exactly the ordering this PR
inverted.

Blast radius depends on which side loses: webhook aborted → 500 → SePay retries
(harmless, idempotent). **Sweeper aborted → the entire tick rolls back**, including
every paid transition and expiry already applied in that transaction, and is not
retried for 15 minutes.

**Probability is low but the window is wide.** The claim branch fires only when an
orphan with that `providerTxnId` exists *and* the booking now resolves — and the
route's `no_booking_ref_in_memo` short-circuit never reaches `processPaymentWebhook`,
so the retry of the common orphan case can't hit it. But the sweeper holds its 200
Booking locks for the *entire* tick duration, so any claim that does fire during a tick
is in the danger zone. It is precisely the recovery scenario this PR exists to serve.

**Fix (pick one):**
- Preferred — make both paths order Booking→PaymentEvent: inside the webhook tx, take
  `SELECT id FROM "Booking" WHERE id = $1 FOR NO KEY UPDATE` before the `updateMany`.
  Cheap (PK lookup), and it converts the deadlock into a clean block-then-proceed —
  and the sweeper's `SKIP LOCKED` will simply skip that booking.
- Alternative — move the claim `updateMany` to *after* `applyPaidStatusTransition`.
  Ordering matches, but the create/claim branch then straddles the currency and amount
  guards; the `SELECT … FOR NO KEY UPDATE` is the smaller change.

Either way, document the lock order in the tx header comment — both files already have
a CONCURRENCY block that should name it.

### `lib/payment/processWebhook.ts:112-119` + `app/api/payments/bank_transfer/webhook/route.ts:73-82` 📈 P2: `PaymentEvent` growth is now coupled to bank-account activity, not booking volume, with no retention path

Every inbound credit to the receiving account with an unparseable memo now writes one
`PaymentEvent` row carrying the **full `rawBody` TEXT**. Nothing prunes them. The
schema comment forbids deletion without bank-statement reconciliation, and no
reconciliation UI or job exists in this PR.

This is the driver behind P1 (orphan set size) and is also a straightforward storage
line item: at 100 unrelated credits/day × ~700 B = ~25 MB/yr of `rawBody` that is
never read except by the sweeper's per-candidate scan.

The idempotency guard is correct — `@@unique([adapter, providerTxnId])` means SePay's
7-attempt retry ladder writes at most one row, and `recordUnmatchedPaymentEvent`
swallows P2002. That is not the concern; the concern is legitimate distinct credits.

**Fix:** file a follow-up for an orphan-reconciliation surface (op console list +
"reconciled / not ours" disposition that either links or archives the row), or at
minimum a retention rule that moves orphans older than N months to a cold table. Pair
with the P1 partial index so the sweeper stays fast in the meantime.

## P3 — ADVISORY

### 1. `lib/payment/processWebhook.ts:232-251` ⏱ P3: +1 statement per webhook delivery — immaterial against SePay's 30 s ack deadline

On the common path (no orphan) the tx now runs `updateMany` (0 rows) **then** `create`,
where it previously ran `create` alone. On the claim path it runs `updateMany` (1 row)
and *skips* the `create` — same statement count as before.

The `where` is a full-key equality on `PaymentEvent_adapter_providerTxnId_key`, so the
scan is an index descent returning ≤ 1 row with `bookingId IS NULL` as a heap recheck —
**no degradation from the third predicate**; it does not make the index unusable, it is
simply a filter applied after the unique lookup. Cost is ~2–3 buffer reads.

Real cost is one extra client↔DB round-trip. Vercel `sin1` to a same-region Postgres is
~1–3 ms; ~10 ms if the DB is cross-region. Against a **30,000 ms** ack budget that is
**≤ 0.03 %**. Not a concern, now or at 100× volume. Recording explicitly so the question
is answered in the record rather than re-litigated.

### 2. `lib/jobs/reconcilePayments.ts:270-280` ℹ️ P3: orphan branch is not adapter-scoped — MoMo/VNPay candidates pay for a bank_transfer-only scan

Only `bank_transfer` can produce an orphan (`unmatched` is populated by that adapter
alone, and `processWebhook.ts:196` gates on `adapter === 'bank_transfer'`). But the
events query has no adapter predicate, so a stuck MoMo or VNPay booking scans the whole
orphan set and then has every row rejected by `matchDegraded`'s `usedAdapters` check.

Adding `AND pe."adapter" = 'bank_transfer'` to the OR-branch is free correctness-wise
and, once the P1 partial index exists, lets the planner skip the branch entirely for
non-transfer candidates. Fold into the P1 fix.

### 3. `lib/jobs/reconcilePayments.ts:244-248` ℹ️ P3 (pre-existing): candidate query has no covering index

`WHERE b."status" = 'awaiting_payment' AND b."createdAt" < $1 ORDER BY b."createdAt" ASC LIMIT 200`
has no matching index. `Booking` carries `@@index([status, reminderSentAt])` and
`@@index([status, refundedAt])` — either can be used as a `status`-prefix scan, but
`createdAt` filtering and the sort are then done above the index. Harmless at current
`awaiting_payment` cardinality; becomes the outer half of the P1 cost as booking volume
grows. `@@index([status, createdAt])` would serve it exactly. Not introduced by this PR
— noting only because P1 multiplies by this query's row count.

### 4. `lib/jobs/reconcilePayments.ts:438-444` ℹ️ P3 (pre-existing, amplified by P1): no-hold bookings are permanent candidates

`holdExpired` requires `booking.holdExpiresAt !== null`, and `Booking.holdId` is
nullable (`prisma/schema.prisma:318`). A booking with no hold that sits in
`awaiting_payment` is never expired and never leaves the candidate set — it is
re-selected and re-scanned every 15 minutes forever. Combined with `ORDER BY createdAt
ASC LIMIT 200`, a sufficient backlog of these permanently starves newer genuinely-stuck
bookings out of the window. Each such row now also pays the P1 orphan scan on every
tick. Worth a follow-up ticket independent of this PR.

### 5. `lib/jobs/reconcilePayments.ts:311-316` ✅ P3 informational: the sweeper's new CAS `$executeRaw` is *not* per-candidate — added time-under-lock is negligible

Correcting the review premise: the CAS `UPDATE` sits inside `if (degradedMatch)`, not in
the loop body unconditionally. It fires only when `matchDegraded` returned a row — i.e.
only in the rare recovery case, not once per candidate. When it does fire it is a
single-row `UPDATE … WHERE "id" = $1::uuid` — a PK index lookup, sub-millisecond plus
one round-trip.

Worst case (all 200 candidates degrade-match, which would mean 200 simultaneous garbled
transfers) adds ~200 round-trips ≈ 0.2–2 s to the locked tick. Realistic case is 0–2
matches per tick ≈ **0 ms**. No action needed. The advisory-locked tick's time budget is
dominated entirely by P1's per-candidate `SELECT`, not by this write.

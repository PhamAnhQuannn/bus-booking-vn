P1 — BLOCKING:
  lib/payment/processWebhook.ts:96-134 (recordUnmatchedPaymentEvent)  🔇 P1: No metric/counter and no
  threshold alert on the orphan-PaymentEvent backlog for a payment-critical write path.
    Every orphan row this PR creates represents real customer money sitting in an anomalous state
    (unlinked, awaiting a heuristic degrade-match). The only signal is a per-event `logger.warn` on
    `unmatched_recorded` — there is no counter of orphan rows created, no counter of orphans still
    unresolved past N minutes/hours, and per the PR's own deferred-work list there is no admin/operator
    UI that surfaces `PaymentEvent` at all (confirmed: `PaymentEvent`/`paymentEvent` appears nowhere
    under `app/**` outside the webhook route, the reconcile cron route, and tests). A steadily growing
    backlog — e.g. if `recoverSepayEvent`'s `transferType==='in'` assumption stops matching a future
    SePay payload variant, or the memo-extraction regex regresses — is invisible until someone runs SQL
    by hand against `PaymentEvent WHERE "bookingId" IS NULL`. This is the exact failure mode Bug B itself
    was: money stuck with zero operational visibility until a human went looking. Shipping the recovery
    path (orphan write + CAS-claim) without any aggregate signal reintroduces the same blind spot one
    layer up.
    Fix (minimum viable signal, pick one): (a) in the reconcile sweeper tick, after the sweep, run
    `SELECT count(*) FROM "PaymentEvent" WHERE "bookingId" IS NULL AND "adapter"='bank_transfer' AND
    "receivedAt" < now() - interval '1 hour'` and `captureMessage('payment.orphan_backlog_aged', {count})`
    when count > 0 — reuses the existing per-tick DB round trip, no new job; or (b) call
    `captureMessage('payment.webhook.unmatched_recorded', {adapter, providerTxnId})` alongside the
    existing `logger.warn` in `recordUnmatchedPaymentEvent` so each orphan at least reaches the Sentry
    issue stream (dedup by message groups repeats into one alertable issue) instead of only a searchable
    log line.

  lib/jobs/reconcilePayments.ts:322-325 (`reconcile.degraded_claim_lost`)  ⚠️ P2: `info` level likely too
  low for an event that can precede a customer-visible wrongful expiry.
    When a booking loses the CAS race for an orphan (another booking already claimed it), the code falls
    through to the expire check and — if the hold has lapsed — that LOSING booking is marked
    `payment_failed_expired`. If the losing booking's own money is genuinely in flight (two customers
    transferred the same amount in the same window, a plausible real-world collision on a fixed fare),
    this is the exact scenario that produces a "I paid but my ticket shows cancelled" support ticket.
    `info` means an operator investigating that complaint has no elevated signal pointing at the claim
    race — they'd have to know to search for `degraded_claim_lost` specifically. Consider `warn` so it is
    visible in the same triage sweep as `unmatched_recorded`, since both represent bookings that need a
    human to reconcile against the bank statement.

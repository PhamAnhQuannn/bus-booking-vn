**Branch:** `feat/customer-auth-email-google` → `master` · **Date:** 2026-08-07 · **Reviewer:** multi-agent team (5 dimensions) + CI-failure diagnosis + skills triage (security / migration-safety / threat-model folded into the dimensions below).

## CI failure diagnosis (root causes)

6 red checks → **2 roots**:

1. **argon2 native crash (Unit, Integration, E2E×2, Flaky-E2E).** `argon2` is a compiled native module; its linux-x64 prebuilt binary **segfaults on the CI runner (Node 20)** while loading fine locally (Win/Node 24 — a different binary). `prisma/seed.ts` calls `hashPassword()` → argon2 → seed dies at exit **139 (SIGSEGV)** before its `Seeded:` summary (proof: exit 139 ≠ the `.catch(process.exit(1))` path — an uncatchable native crash, so the code's `try/catch → scrypt` fallback can't intervene). The Unit job dies the same way (246/247 files pass; one argon2 test worker `emitUnexpectedExit`). Integration + both E2E jobs all run `pnpm prisma db seed`, so the seed crash fails them too.
2. **Data-Leak audit (independent).** `scripts/audit/data-leak-grep.sh`: **A4** sameSite-lax count 16 > baseline 14 (the two new OAuth cookies), **A7** `proxy.ts:195` comment literally contained `OTP_PEEK_ENABLED`.

### Decision (with owner)
argon2id → **opt-in behind `AUTH_ARGON2_ENABLED` (default OFF → scrypt N=16384**, the pre-P19 baseline; not a regression vs today). Deterministic-green now; flip ON in prod after a Vercel-Linux preview verifies argon2 loads. `needsRehash`/rehash-on-verify auto-upgrade scrypt→argon2id on next login once enabled — no manual account migration. Owner waived the prod-crash concern (no real users yet). This is the author's own documented **G-BUILD** contingency, downgraded from a build-blocker to a config flip.

### NOTE — verified acceptable / deferred

- **OIDC `nonce` absent** (`googleIdToken.ts`) — defensible: id_token arrives via the back-channel code exchange (TLS + PKCE `code_verifier`), no front-channel injection path. Nonce would be defense-in-depth only.
- **`state` compare not constant-time** (`callback/route.ts`) — not exploitable: the expected `state` lives in an HMAC-signed HttpOnly cookie the attacker can't read/forge, so there's no timing oracle.
- **`googleIdToken` also accepts bare `accounts.google.com`** — safe over-acceptance; Google legitimately issues both `iss` forms.
- **`Account` one-provider-per-customer** is app-enforced only (`@@unique([provider, providerAccountId])` guards sub-reuse). A `@@unique([customerId, provider])` DB guarantee is optional; not added (extra migration, app path already enforces).
- **L2 suspension re-read outside the tx** — a customer suspended mid-flow could mint one short-lived access token; backstopped by `requireCustomerAuth` (next check → 403) + suspend-time session revoke.
- **Per-realm refresh-secret cutover** (`REFRESH_TOKEN_SECRET_{CUSTOMER,OPERATOR,ADMIN}`) has no dual-secret grace → one-time forced re-login for all realms on deploy. By design (env boot-fails if unset); already a PR go-live gate (**G-SECRET**).

## Migration & data-model (all PASS)

3 migrations are additive/safe: `emailVerifiedAt` nullable + `createdAt` backfill (no lock); the narrowed partial unique index `WHERE email IS NOT NULL AND deletedAt IS NULL` correctly frees deleted-customer emails; `OtpAttempt` XOR CHECK matches every writer; `Account` FK `ON DELETE CASCADE` + `@@unique`/`@@index`, stores only `sub` + audit email (no tokens). Rollback caveat noted: recreating a FULL email unique index can fail if a live+deleted duplicate now exists (repo is forward-only — informational).

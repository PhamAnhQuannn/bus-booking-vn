P1 — BLOCKING:

  lib/core/db/client.ts:14-25  🔇 P1: The pool change creates a new production failure mode
  and instruments none of it. Pool saturation is invisible by construction, and this stack
  has no tracing to reconstruct it after the fact.

    SCOPE NOTE — declared: `lib/core/db/client.ts` is infrastructure, not a handler or job,
    so it sits outside this skill's literal detection scope. Reported anyway: the whole
    point of an observability gate is "will oncall be able to see this at 3am", and this
    two-line change is the single largest new failure mode in the PR. Skipping it on a
    path technicality would be reviewing the letter of the rule.

    The new `Pool({ max: 1, connectionTimeoutMillis: 10_000 })` emits:
      · no `pool.on('error', ...)` handler — a backend-terminated idle connection surfaces
        as an unhandled `'error'` event on the Pool emitter,
      · no log or counter on acquire wait,
      · nothing on saturation.
    Prisma is configured `log: ['error']` outside development, so it adds nothing either.

    `pg.Pool` already exposes exactly the three numbers needed, for free, as synchronous
    properties: `pool.totalCount`, `pool.idleCount`, `pool.waitingCount`. Nothing reads
    them. At `max: 1`, `waitingCount` IS the queue depth — the single most diagnostic
    number in the system after this change — and it is discarded.

    What oncall actually gets when the failure fires: Sentry receives
    `Error: timeout exceeded when trying to connect` from pg, ~10s after the request began,
    attributed to whichever unlucky route happened to be *waiting* — never to the route
    that was *holding* the connection. Since the holder is typically `createHold` parked on
    `pg_advisory_xact_lock` (lib/core/db/holdRepo.ts:97, open issue #362), the errors
    cluster on search, reports, and webhooks while the culprit reports success. Every
    signal points away from the cause.

    ADR-007's "no distributed tracing" decision was sound for a monolith where request
    latency is dominated by that request's own work. This PR breaks that premise: with one
    shared connection, one request's latency is now a function of *other* requests'
    behaviour. That is precisely the coupling tracing exists to untangle, and it is the
    coupling this stack deliberately cannot see. The decision is not wrong, but this PR
    changes its inputs and does not revisit it.

    Fix — cheap and specific, all in `createPrismaClient()`:
      1. `pool.on('error', (err) => logger.error({ err }, 'db.pool.error'));`
      2. Log on saturation before acquiring, e.g. when `pool.waitingCount > 0`:
         `logger.warn({ waiting: pool.waitingCount, total: pool.totalCount,
                        idle: pool.idleCount, max }, 'db.pool.saturated')`
      3. On a caught acquire timeout, `captureException` with the same three counters
         attached, so Sentry groups by saturation rather than by victim route.
    Without at least (1) and (2), the #362 incident is undiagnosable from telemetry.


P2 — SHOULD FIX:

  app/api/health/route.ts:38-43  ⚠️  P2: The bare `catch { }` discards the diagnosis from
  the one probe that will actually detect this PR's failure mode.

        } catch {
          return NextResponse.json(
            { status: 'degraded' },
            { status: 503, headers: NO_STORE }
          );
        }

    The good news first, because it matters: `/api/health` pings the DB with
    `prisma.$queryRaw(SELECT 1)` on the **same shared singleton**, hence the same pool. So
    at `max: 1` a starved instance genuinely does fail its readiness probe and BetterStack
    genuinely does alert. Detection is not missing.

    Diagnosis is. The catch binds no error and logs nothing — it converts every possible
    cause (pool acquire timeout, Neon cold start, credentials, network partition, backend
    crash) into one indistinguishable `{status:'degraded'}`. Sentry never sees it either,
    because nothing throws past the catch. The alert says "degraded"; the logs say nothing;
    there are no traces by design. That is a page with no next step.

    This is pre-existing, not introduced here. It becomes P2 *because of* this PR: before,
    a 3s pool timeout on a 5-connection pool was an unlikely path through this catch; after,
    it is the expected path, and the probe is the primary detector.

    Second-order effect worth noting: the probe's own worst-case latency rises 3s → 10s
    with `connectionTimeoutMillis`. Many uptime probes default to a 10s HTTP timeout, so
    the observed symptom may flip from a clean 503 to a probe timeout — a different alert
    class, often routed differently, and one that cannot carry the response body.
    Fix: `catch (err) { logger.error({ err }, 'health.db_ping_failed'); ... }` — bind the
    error, log it structured, keep the 503 response identical.

  app/api/op/reports/payouts/[id]/retry/route.ts:25-66  ⚠️  P2: Money-mutating handler
  emits no log and writes no audit row — while its admin twin does both for the same
  operation.

        app/api/admin/finance/payouts/[id]/retry/route.ts:54-56
          → writes { action: 'payout-retry', target: payoutId, argsRedacted: ... }
        app/api/op/reports/payouts/[id]/retry/route.ts

    Both endpoints call the same `retryPayout` service and drive the same
    `failed → processing` state transition on the same row. An operator-initiated retry
    leaves no trace; an admin-initiated one leaves a full audit record. When a payout is
    later disputed, "who retried this and when" is answerable for one path and not the
    other. ADR-007 D3 chose domain-partitioned audit precisely so money-path mutations are
    reconstructible.

    Pre-existing, and the handler is modified rather than new — so this is P2, not the
    mechanical P1 the "new mutation handler" rule would assign. It is called out here
    because this PR rewrote the success branch of this exact handler (commit 8618573,
    changing the response contract), which was the moment to add the line. It also means
    the wire-contract change flagged P1 in the /backcompat-review ships with zero telemetry
    on the endpoint that carries it — if a consumer breaks on the new string types, nothing
    records that the route was even called.
    Fix: `logger.info({ payoutId, operatorId: authCtx.operatorId }, 'payout.retry.requested')`
    on the success branch, or an audit row matching the admin route.


P3 — ADVISORY:

  lib/jobs/processPayouts.ts:141-150  📊 P3: A fully successful sweep emits nothing.

    The job logs only when `skipped > 0`. A run that settles 500 payouts logs zero lines;
    a run that settles zero and skips zero logs zero lines. Both return
    `{ rowsAffected, status: 'success' }` to the cron wrapper.

    Credit where due: the `skipped > 0` branch already dodges the trap CLAUDE.md records
    on 2026-07-24 — *"a fully-starved tick reports `success, rowsAffected:0`, identical to
    idle"* — so the unverified-account starvation case IS distinguishable. Good.

    What is missing is duration and volume on the success path, and that matters more after
    this PR than before: the sweep is unbounded (`FOR UPDATE SKIP LOCKED` with no `LIMIT` —
    open issue #364, and the only sibling sweep without a cap) and it now runs on the
    instance's **only** connection, holding row locks on every due payout for its full
    duration. Today `settlePayout` is a no-network stub so runs are fast; the moment real
    bank HTTP lands there, sweep duration becomes the number that explains an outage, and
    nothing records it.
    Fix: one line before the return —
    `logger.info({ processed, skipped, durationMs: Date.now() - startedAt }, 'processPayouts.completed')`.
    Failure path is already covered (`captureException` at :133 with `area: 'payout'`).

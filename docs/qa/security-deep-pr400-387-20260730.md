## RESOLUTION: `sharp` — the open question, closed

**`sharp@0.34.5`, via `next@16.2.10 > sharp` (an optional dependency of `next`). `GHSA-f88m-g3jw-g9cj`, HIGH, `< 0.35.0`, published 2026-07-21 — "sharp inherited vulnerabilities in libvips: CVE-2026-33327, CVE-2026-33328, CVE-2026-35590, CVE-2026-35591".**

Every one of those is a **libvips image-decoding** bug. Exploiting any of them requires getting attacker-chosen bytes into the decoder. In this repo that is impossible, for four independent reasons — none of which depends on where the app is deployed:

1. **One call site, and its input is a module constant.** `components/brand/Logo.tsx:1` is the only `import Image from 'next/image'` in the tree. Its `src` comes from a frozen `LOGOS` map at `Logo.tsx:11-16` — four hardcoded strings (`/brand/logo-horizontal.png`, `/brand/logo-horizontal-white.png`, `/brand/logo-mark.png`, `/brand/logo-mark-white.png`). No prop, no param, no DB value reaches `src`.
2. **The rest of the app deliberately bypasses the optimizer.** Three components carry an explicit `eslint-disable @next/next/no-img-element` whose justification text is *"next/image+sharp not used in this app"*. Someone already made this decision.
3. **Remote images are rejected outright.** `next.config.ts` has **no `images` key**, so `images.remotePatterns` / `images.domains` are empty. `/_next/image?url=https://anything/…` is refused by Next before any fetch. Only same-origin paths are optimizable.
4. **The one user-supplied binary path is not same-origin.** The only place a user can upload bytes is operator KYB documents via presigned S3 (`app/api/op/kyb/upload-url/route.ts`). Those live on the S3 host, which is not in `remotePatterns` (which is empty), so the optimizer will not fetch them. Nothing else in `app/api/**` emits an `image/*` content type.

**Conclusion: the `sharp` HIGH is not exploitable in this application.** The Vercel-vs-local-sharp question is therefore *moot* — which is a better outcome than answering it, because this conclusion survives a change of deploy target, and the Vercel answer would not.

Two notes to keep with it: `next@16.2.11` (this PR) *does* close the other image-path issue, `GHSA-q8wf-6r8g-63ch` (MODERATE, DoS in the Image Optimization API via SVGs) — so the image surface is strictly better after #400. And if you want the audit number itself clean, `sharp` is overridable (`pnpm.overrides.sharp: ">=0.35.0"`) — but on the evidence above that is cosmetic, and it means overriding a pinned optional dependency of `next`, which carries its own regression risk. **Recommend: leave it, and record this analysis so the next reviewer does not re-open it.**

`fast-uri@3.1.2` carries **two HIGH** advisories — `GHSA-4c8g-83qw-93j6` (`>=3.0.0, <3.1.3`) and `GHSA-v2hh-gcrm-f6hx` (`>=3.0.0, <=3.1.3`), both host-confusion, both fixed in 3.1.4. The PR body dismisses them with:

The `withSentryConfig` observation is itself **true** — `next.config.ts:53` is a bare `export default nextConfig`, no wrapper — but it gates only one of three parents. Deleting Sentry tomorrow would not remove `fast-uri`, which is precisely what a reader of that sentence would conclude.

**Qualifier, stated plainly:** the *conclusion* survives for reasons the body never gives. `shadcn` and `prisma` are both CLI/build tools that no application module imports (`shadcn`'s only reference is a build-time CSS import — see P2-1; `@prisma/dev` only runs under `prisma dev`). It is also **moot after #387**, which takes `fast-uri` to 3.1.4 on all three paths.

**Fix:** amend the #400 body — replace "reachable only through `@sentry/webpack-plugin`" with the three-path enumeration and the real reason (all three parents are build/CLI tooling, none loaded at request time). Do **not** hold the merge for this; the code change is correct.

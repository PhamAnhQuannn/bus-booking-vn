## PR #386 — `lucide-react` 1.22.0 → 1.27.0 · **no perf concern**

This was flagged as the main event. It is not a problem, and the reason is measurable rather than inferred.

### The import shape is correct at every single call site

64 source files import from `lucide-react`. **Zero use a namespace or default import.** Verified:

```
grep -rn "import \* as .* from 'lucide-react'|from 'lucide-react/'" app components
→ NONE — all imports are named per-icon
```

Every site matches the FD-027:202 rule verbatim, e.g.:
- `components/search/SearchForm.tsx:5` — `import { MapPin, ArrowLeftRight, ArrowRight, Minus, Plus, Loader2 } from 'lucide-react';`
- `components/layout/SiteHeader.tsx:17` — `import { ChevronDown, LogInIcon, MenuIcon, XIcon } from 'lucide-react';`
- `components/op/navConfig.ts:41` and `components/admin/navConfig.ts:21` — multi-line named imports, still per-icon.

### Measured: how much of the library is actually reachable

Counted distinct named imports across `app/` + `components/`, resolved each to its per-icon ESM module in `node_modules/lucide-react/dist/esm/icons/`, and summed real file sizes:

| Metric | Measured value |
|--------|----------------|
| Distinct icons imported | **82** (+1 type-only import `LucideIcon`, +1 alias `Route as RouteIcon`) |
| Sum of the 82 per-icon ESM modules | **48,347 bytes** raw |
| All 1,993 icon modules in the package | **1,399,119 bytes** raw |
| **Share of the library reachable from source** | **3.46 %** |

Raw, unminified, ungzipped — these are pre-bundler bytes. They establish the *ceiling* on what tree-shaking must keep, not the shipped size.

### The three things that decide +0 KB vs +hundreds of KB — all three hold, and none changed

**(1) Package shape is byte-identical between the two versions.** Pulled from the npm registry (published `package.json`, not the local install):

| Field | 1.22.0 | 1.27.0 |
|-------|--------|--------|
| `main` | `dist/cjs/lucide-react.js` | `dist/cjs/lucide-react.js` |
| `module` | `dist/esm/lucide-react.mjs` | `dist/esm/lucide-react.mjs` |
| `sideEffects` | `false` | `false` |
| `typings` | `dist/lucide-react.d.ts` | `dist/lucide-react.d.ts` |
| `exports` | *(absent)* | *(absent)* |

**No `exports` map was added, `sideEffects: false` is retained, and the ESM/CJS layout is unchanged.** This is the specific risk that was raised, and it is disproved directly from the registry.

**(2) Next.js strips the barrel before the bundler ever sees it.** `node_modules/next/dist/server/config.js:988` — Next 16.2.10 injects `'lucide-react'` into `experimental.optimizePackageImports` **by default**, appended to any user-provided list. `next.config.ts` does not (and need not) configure it. This rewrites `import { Bus } from 'lucide-react'` into a direct deep import of `dist/esm/icons/bus.mjs`, so the 233 KB re-export barrel (`dist/esm/lucide-react.mjs`) is never traversed.

**(3) `sideEffects: false` lets webpack drop whatever survives** even if (2) were bypassed.

### Disk growth is not bundle growth

`dist.unpackedSize` 30,768,767 → 31,001,784 bytes (**+233 KB, +0.76 %**), `dist.fileCount` 4,026 → 4,054 (**+28 files ≈ 7 new icons** × esm/cjs × js/map). Those are new icons nobody imports. With per-icon imports + `optimizePackageImports`, unimported icons cost **zero** bundle bytes. Upstream release notes for 1.23.0–1.27.0 record icon additions and framework-compat fixes only — no export-map, `sideEffects`, tree-shaking, or bundle-layout change.

> **Not measured:** the exact gzipped KB the 82 icons contribute per route, and whether that still fits the ~3 KB FD-027:82 line item. Nothing in this diff moves that number in either direction — the icon *set* is unchanged, only the library version is — so the budget position is identical before and after. Settling it absolutely would need `pnpm build` on `master` vs the PR head and a diff of `.next/analyze` or the per-route "First Load JS" table. **There is no `.next/` build in the tree to measure against**, and building would write to the shared working tree, which this review is forbidden from doing.

**Icon-rename risk:** low, and gated. Lucide retains aliases across minors, and CI runs `pnpm tsc --noEmit`, which fails on any removed export. A dropped icon name is a build failure, not a silent regression.

## PR #384 — `@sentry/nextjs` 10.65.0 → 10.68.0 · **note**

### Client bundle weight, as configured

Context taken as given from the prior review (not re-derived): `next.config.ts` never calls `withSentryConfig` — confirmed by grep — and both init sites set `tracesSampleRate: 0` (`instrumentation.ts:26`, `instrumentation-client.ts:88`). The perf question that follows is what the browser actually pays.

**The two init sites use opposite import strategies, and this is the whole story:**

- `instrumentation.ts:17` (server) — `const Sentry = await import('@sentry/nextjs');` **inside** the `if (process.env.SENTRY_DSN && ...)` guard. Lazy. Nothing loads when the DSN is unset.
- `instrumentation-client.ts:15` (browser) — `import * as Sentry from '@sentry/nextjs';` at **module top level**, outside the guard. The `if (dsn)` at line 84 gates only `Sentry.init()`, not the import.

The static client import is safe **only** because two things hold together: `@sentry/nextjs` declares `sideEffects: false` (verified in the installed `package.json`), and `NEXT_PUBLIC_SENTRY_DSN` is inlined at build time — so when it is unset, `if (undefined)` is dead code, DCE removes the `init` call, the namespace binding becomes unused, and `sideEffects: false` permits dropping the module entirely. `.env.example:170` states this intent explicitly: *"no browser SDK when unset."*

`tracesSampleRate: 0` does **not** shrink the bundle — it suppresses span *sending* at runtime. The tracing integration code is still linked in whenever the DSN is set.

**Version delta:** Sentry's own published size-limit figures hold the `@sentry/nextjs` client bundle flat at **49.48–50.2 KB** across 10.65 → 10.68. 10.66.0's build changes ("include bundler CJS exports", Nuxt module rebuilt in-house) do not touch the Next.js client entry. **No client-bundle regression from this bump.**

### Cold start

`@apm-js-collab/code-transformer` 0.15.0 → 0.18.1, `code-transformer-bundler-plugins` 0.5.0 → 0.7.1, and OTel `core`/`resources`/`sdk-trace`/`sdk-trace-base` 2.9.0 → 2.10.0. 67 distinct packages change in the lockfile.

The bundler plugins are **build-time only** and inert here — `withSentryConfig` is never called, so they are never registered with webpack. The runtime module hooks (`import-in-the-middle@3.3.1`, `require-in-the-middle@8.0.1`, present in the tree) are reached only via `@sentry/node`'s OTel auto-instrumentation, which loads only through the lazy `await import()` in `instrumentation.ts`. **With `SENTRY_DSN` unset, none of it is imported at runtime and the cold-start delta is zero.** With it set, 10.68 is directionally *better*: the Node SDK now registers Sentry's minimal `SentryTracerProvider` by default (since 10.64.0), bypassing the full OTel pipeline — an improvement for serverless cold start on Vercel.

Neither `.env.local` nor `.env.production.local` contains a `SENTRY_DSN` or `NEXT_PUBLIC_SENTRY_DSN` line. Production env lives in the Vercel dashboard and is **not visible from this review**, so which branch prod is on is unknown.

> **Not measured:** cold-start ms delta, and the shipped client KB in the DSN-set configuration. Settling it: `pnpm build` with `NEXT_PUBLIC_SENTRY_DSN` set on `master` vs PR head, comparing First Load JS for a customer route.

## PR #383 — `@tailwindcss/postcss` 4.3.0 → 4.3.3 · **no perf concern**

devDependency, but it compiles the CSS that ships. Both angles are favorable.

### (a) Emitted CSS gets smaller

The 4.3.1 changelog "Changed" section confirms the hypothesis verbatim:

> - "Generate `0` instead of `calc(var(--spacing) * 0)` for spacing utilities like `m-0`"
> - "Generate `var(--spacing)` instead of `calc(var(--spacing) * 1)` for spacing utilities"

4.3.3 adds a correctness follow-up — *"Ensure `--spacing(0)` is optimized to `0px` instead of `0` so it remains a `<length>`"* — which applies to the `--spacing()` function in arbitrary values, not to the `m-0`-style utilities.

**Measured exposure in this codebase:** 45 unique base spacing utilities at value 0 or 1 (22 at `0`, 23 at `1`), plus 14 more in variant forms (`lg:gap-0`, `md:mt-0`, `after:inset-x-0`, `before:w-1`, …) — roughly **59 emitted declarations** affected.

Per-declaration minified saving: `calc(var(--spacing)*0)` (22 ch) → `0` (1 ch) = 21 bytes; `calc(var(--spacing)*1)` (22 ch) → `var(--spacing)` (14 ch) = 8 bytes. Order of magnitude: **~800 bytes raw**, and considerably less gzipped — `calc(var(--spacing) * N)` is a highly repetitive string that gzip already compresses well, so removing it recovers far less than the raw delta suggests.

Against FD-027:70's **30 KB gzipped CSS** budget for customer routes this is noise. **Direction is favorable; magnitude is negligible.**

> **Not measured:** the actual emitted-CSS byte delta. The count above is source-side utility usage, not compiler output. Settling it: `pnpm build` on both refs and `gzip -c .next/static/css/*.css | wc -c`.

Also relevant: 4.3.1's *"Remove deprecation warnings by using `Module#registerHooks` instead of `Module#register`"* removes Node deprecation noise from build logs.

### (b) Build/install time improves via dedup

The lockfile drops **9 duplicate package instances**:

```
tailwindcss@4.3.0            postcss@8.5.14      enhanced-resolve@5.21.3
baseline-browser-mapping@2.10.43   postcss@8.5.20      nanoid@3.3.12
browserslist@4.28.6          electron-to-chromium@1.5.393
update-browserslist-db@1.2.3(browserslist@4.28.6)
```

Net `-31` lockfile lines (`+84 / -115`). Dropping a second full `tailwindcss@4.3.0` copy is the meaningful one — fewer packages to link on `pnpm install --frozen-lockfile`, which runs in **five separate CI jobs**. Small but strictly positive, across install *and* build.

## Findings

### P3 — ADVISORY

**P3-1 · `.github/workflows/ci.yml:221` — ⏱ Playwright browsers are re-downloaded on every CI run; no cache step.**
`pnpm exec playwright install --with-deps chromium webkit` runs with no `actions/cache` keyed on the Playwright version. Chromium + WebKit ≈ **580 MB extracted / ~200 MB download**, paid on every e2e job — and the job is a 2-way matrix (`chromium`, `mobile-390`), so **twice per CI run**, plus again in `flaky-e2e` (`ci.yml:299`).
*This is pre-existing and not introduced by #385* — and it is precisely why #385's ~+2 MB download delta is irrelevant: there is no cache to invalidate.
Fix: cache `~/.cache/ms-playwright` keyed on the resolved `playwright-core` version. Likely worth **more CI wall-clock than any of these four bumps combined**.

**P3-2 · `.github/workflows/ci.yml:227` — ℹ️ #385 unlocks `retryStrategy: 'isolated'`, currently unused.**
1.62.0 adds a retry strategy that defers retries to the end in a single worker, reducing cross-test interference. This repo already maintains a `flaky-e2e` quarantine lane, so flake is a known cost. Opt-in — merging #385 changes nothing by itself. Consider evaluating in `playwright.config.ts` as a follow-up.

**P3-3 · `instrumentation-client.ts:15` — 📦 Client Sentry import is static; elimination depends on build-time DCE.**
Unlike the server hook's lazy `await import()` (`instrumentation.ts:17`), the browser SDK is imported at module top level and only `Sentry.init()` is guarded. Removal relies on `NEXT_PUBLIC_SENTRY_DSN` being statically absent + `sideEffects: false`. That chain does hold today, and `.env.example:170` documents the intent — but it is an *implicit* guarantee resting on minifier behavior, not an explicit one.
*Pre-existing; #384 does not change it.* If the DSN is ever set in prod, ~50 KB min+gzip enters every client route with `tracesSampleRate: 0` — i.e. paying for the tracing code without using it. A CI assertion on customer-route First Load JS (FD-027:88 already specifies a 200 KB hard gate) would make this explicit rather than assumed.

**P3-4 · `documentation/frontend-design/FD-027-performance-budget/README.md:86-88` — ℹ️ The bundle budget has no automated enforcement.**
FD-027 specifies "`next build` output analyzed per route in CI", alert at 150 KB and **block merge at 200 KB** gzipped for customer routes. No such step exists in `ci.yml`. This is why #386 and #384 — the two PRs that do reach the browser — cannot be verified against their own stated budget without a manual local build. Analogous in shape to the 2026-07-25 `import-x/no-cycle` entry in the Mistake Log: a documented gate that emits nothing is not evidence of a clean tree.

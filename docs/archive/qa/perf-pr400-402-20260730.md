## Q4 — Tailwind risk on the new `COLUMN_CLASS` lookup

**Cleared. No runtime-assembled class fragment exists.**

The repo has no `tailwind.config.*`; it is Tailwind v4 driven by `@import "tailwindcss"`
in `app/globals.css`. v4's extractor is a plain-text scan over source — it does not
evaluate JS — so a class is generated **iff its complete string appears literally in a
scanned file.** Head of `components/home/OperatorShowcase.tsx`:

```ts
const COLUMN_CLASS: Record<number, string> = {
  1: 'grid-cols-1 sm:grid-cols-2',
  2: 'grid-cols-1 sm:grid-cols-2',
  3: 'grid-cols-1 sm:grid-cols-2 lg:grid-cols-3',
  4: 'grid-cols-1 sm:grid-cols-2 lg:grid-cols-4',
};
const columns =
  COLUMN_CLASS[cards.length] ?? 'grid-cols-1 sm:grid-cols-2 lg:grid-cols-3 xl:grid-cols-5';
...
<div className={`grid gap-4 ${columns}`}>
```

Every utility is a **complete literal**. Nothing of the shape `` `grid-cols-${n}` `` —
which is the pattern that silently produces an ungenerated class — appears anywhere in
the file. The template literal contributes `grid` and `gap-4` as literals; the
interpolated `${columns}` only ever holds one of the five literal strings above, all of
which are themselves present in the same file.

Cross-checked against corroborating usage elsewhere, so this does not even depend on
the new file being scanned:

- `lg:grid-cols-4` — 7 other occurrences (`app/(customer)/page.tsx:417`,
  `app/admin/(console)/page.tsx:149`, `components/op/FilterBar.tsx:56`, …)
- `sm:grid-cols-2` — 10+ other files
- `xl:grid-cols-5` — only in this file, but as a **literal** in the fallback string

**Caveat, scoped correctly.** The 2026-07-18 mistake-log entry (fresh Tailwind class
computing to its unset default) was a **Turbopack dev-server stale-rescan** bug, not a
production-build bug — `touch` did not trigger the Windows watcher and the served
stylesheet still held the old class. It can recur here in `pnpm dev` on the first edit,
and the diagnosis recipe from that entry still applies (fetch the served stylesheet
in-page and grep it for the class). It does **not** affect `pnpm build`. Not a merge
concern.

## PR #400 findings

**P2-1 — `pnpm-lock.yaml` · 📦 69 `libc:` platform-filter fields dropped to 0 — lockfile regenerated by an older pnpm than CI runs**

This is the finding the PR body does not mention, and it is a regression rather than a
win.

Measured: base has **69** `libc:` fields, head has **0**. Zero added anywhere. The
removals span packages this PR has no business touching — `@img/sharp-libvips-*`,
`@rollup/rollup-linux-*`, `@tailwindcss/oxide-*`, `@unrs/resolver-binding-*`,
`lightningcss-*` — none of which are `next`, `postcss` or `@hono/node-server`. A
dependency bump does not strip metadata from unrelated packages. **The lockfile was
regenerated by a pnpm version that does not emit the `libc` field.** The pnpm in this
checkout is `10.28.0` and the base lockfile *has* the fields, so the PR's isolated
worktree (the PR body confirms it used one with its own `pnpm install`) ran an older
pnpm.

`libc` is what lets pnpm skip musl-only optional native binaries on a glibc host, in
concert with `os`/`cpu`. **27 of the 69** were `libc: [musl]`:

```
@img/sharp-libvips-linuxmusl-{arm64,x64}   @img/sharp-linuxmusl-{arm64,x64}
@next/swc-linux-{arm64,x64}-musl           @rolldown/binding-linux-{arm64,x64}-musl
@rollup/rollup-linux-{arm,arm64,loong64,ppc64,riscv64,x64}-musl(eabihf)
@tailwindcss/oxide-linux-{arm64,x64}-musl  @unrs/resolver-binding-linux-*-musl (×7)
lightningcss-linux-{arm64,x64}-musl (×4)
```

The remaining 42 were `libc: [glibc]`.

CI runs `pnpm install --frozen-lockfile` on `ubuntu` (glibc, x64) in five jobs, with
`PNPM_VERSION: '10'` — a **floating major**, so `pnpm/action-setup@v6` resolves to the
newest 10.x at run time, i.e. a pnpm that *does* understand `libc`. `--frozen-lockfile`
will not rewrite the file, so it must install from metadata that no longer carries the
filter. On a linux-x64 glibc runner the musl x64 variants — `@next/swc-linux-x64-musl`,
`@img/sharp-linuxmusl-x64`, `@img/sharp-libvips-linuxmusl-x64`,
`@tailwindcss/oxide-linux-x64-musl`, `@rollup/rollup-linux-x64-musl`,
`@rolldown/binding-linux-x64-musl`, `@unrs/resolver-binding-linux-x64-musl` ×3,
`lightningcss-linux-x64-musl` ×2 — pass the `os`/`cpu` gate and lose the only thing that
was excluding them.

**The megabyte cost is NOT MEASURED** — see NOT MEASURED #3. `@next/swc-*` binaries run
to the low hundreds of MB unpacked and sharp's libvips to ~10 MB, so the plausible range
is large, but I have not put a number on it and neither should the PR.

*Fix (one line, and it fixes the cause not the symptom):* add
`"packageManager": "pnpm@10.28.0"` to `package.json` and change `PNPM_VERSION` in
`.github/workflows/ci.yml:15` from `'10'` to the same exact version, then regenerate the
lockfile once. Corepack/`pnpm/action-setup` then pin dev and CI to one pnpm and the
lockfile stops oscillating.
*Or, minimally, to unblock this merge:* regenerate `pnpm-lock.yaml` under pnpm ≥ the
version that emits `libc` and confirm `grep -c "^    libc:" pnpm-lock.yaml` returns
**69**, not 0.

**P3-4 — `package.json` / `.github/workflows/ci.yml:15` · 🔧 no `packageManager` pin, CI pins a floating major**
`package.json` has no `packageManager` field and no `engines` block; CI sets
`PNPM_VERSION: '10'`. Nothing keeps a contributor's pnpm and CI's pnpm on the same
minor, and a lockfile is a format-versioned artifact. P2-1 is the first observed symptom;
it will recur. This is the root cause, hence its own row.

**P3-5 — PR #400 body · 📝 the postcss consolidation claim does not match the merge base**
The body states: *"`postcss` consolidating from three resolved copies (8.5.14, 8.5.16,
8.5.20) to one (8.5.25)"*. Measured at base `68933d28`: there are **two** copies

The `@hono/node-server` claim (2.0.4 + 2.0.6 → 2.0.12) **is correct** as written, and the

This matters beyond pedantry: on a squash-merge the PR body becomes the permanent master

*Fix:* correct the sentence to "two resolved copies (8.5.16, 8.5.25) to one (8.5.25)"

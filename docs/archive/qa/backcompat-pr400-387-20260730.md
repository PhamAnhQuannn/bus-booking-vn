## THE THREE DIRECT ANSWERS

### 1. Does the `next` 16.2.10 → 16.2.11 patch change which paths middleware runs on? **NO — not for this repo. Verified, not assumed.**

`16.2.11` contains exactly one middleware-related commit: `3c48c7a` *"[16.x] Fix Turbopack middleware matcher with i18n single locale"* (fixes `GHSA-6gpp-xcg3-4w24`). The upstream fix is a **build-time** change in Turbopack's Rust crate `crates/next-api/src/middleware.rs` — not a runtime request-handling path. The entire behavioural diff is one boolean:

```rust
-  let has_i18n_locales = i18n.as_ref().map(|i18n| i18n.locales.len() > 1).unwrap_or(false);
+  let has_i18n_locales = i18n.is_some();
```

**This repo has no `i18n` configuration at all.** Verified against `origin/master`, not the working tree:

- `git show origin/master:next.config.ts | grep i18n` → no match.
- `git grep -l "i18n" origin/master -- '*.ts' '*.js' '*.mjs' '*.json'` → **zero tracked files**.

With `i18n == None`, the old expression evaluates `.unwrap_or(false)` → `false`, and the new expression evaluates `.is_some()` → `false`. **Identical output. The generated middleware manifest is byte-for-byte unchanged.**

**Consequence — the re-check you asked for is not required:**

- `proxy.ts:355-358` matcher `'/((?!_next/static|_next/image|favicon.ico).*)'` — unaffected.
- `proxy.ts:76` `CSRF_EXEMPT` exact-match `Set` — unaffected.
- `proxy.ts:82` `CSRF_EXEMPT_PREFIXES` — unaffected.
- `proxy.ts:92` `OP_AUTH_FREE_PATHS`, `proxy.ts:107` `ADMIN_AUTH_FREE_PATHS` — unaffected.

No path-normalization, encoded-character (`%2e`/`%2f`), trailing-slash, RSC/prefetch, or `x-middleware-*`/`x-nextjs-*` header handling is touched anywhere in 16.2.11. The bypass was a **matcher-generation** defect, never a runtime header or encoding bug.

The other three 16.2.11 fixes (`d303326` rewrite-param encoding, `b512063` custom-server redirect origin, `ac1eff3` MPA form-submission check) touch rewrite/redirect/Server-Action paths, not middleware matching. `redirects()` in `next.config.ts` uses a static `:id` passthrough with no dynamic hostname, so `d303326` is also a no-op here.

### 2. Is the `@hono/node-server` major-boundary override safe? **YES in practice, but the framing is wrong and a strictly better range exists.**

**The major boundary is already crossed on `origin/master` today.** The existing floor `>=1.19.13` is *unbounded above*, so pnpm resolves the newest match. `git show origin/master:pnpm-lock.yaml` already contains `@hono/node-server@2.0.4` and `@hono/node-server@2.0.6`. PR #400 does **not** cross the boundary — it consolidates 2.0.4 + 2.0.6 → **2.0.12** and makes the pre-existing 2.x-forcing explicit.

**Consumers and their declared ranges** (read from installed `package.json` and registry metadata):

| Consumer | Declares `@hono/node-server` | 2.x compatible? | Reached via |
|---|---|---|---|
| `@prisma/dev@0.24.3` | `"1.19.11"` — **exact pin** | **No** | `prisma` (prod dep) |
| `@modelcontextprotocol/sdk@1.29.0` | `"^1.19.9"` — 1.x only | **No** | `shadcn` (prod dep) |
| `@modelcontextprotocol/sdk@1.30.0` *(arrives with #387)* | `"^1.19.9 \|\| ^2.0.5"` | **Yes** | `shadcn` |

So the override does violate two declared ranges — exactly the class `pnpm.overrides` hides. **But both documented v2.0.0 breaking changes are provably inapplicable here:**

1. **Dropped Node 18** (`engines.node >= 20`). CI runs Node 20 (`.github/workflows/ci.yml:14`); `next@16.2.11` itself requires `>=20.9.0`. Satisfied.
2. **Removed the `@hono/node-server/vercel` subpath export.** Grepping both consumers' shipped `dist/` for `@hono/node-server[a-z/]*`: `@prisma/dev` → 3 hits, `@modelcontextprotocol/sdk` → 8 hits, **all bare specifiers, zero `/vercel` subpath imports.** Not reached.

Correcting one common misconception: **v2 is not CJS-dropping.** `"type": "module"` was added and `main` moved to `.mjs`, but the `exports` map retains a `require` condition pointing at `./dist/index.cjs`. Any `exports`-aware resolver (all Node ≥20) still gets working CJS. `@prisma/dev` ships a dual build (`main: ./dist/index.cjs`) and resolves fine.

Neither consumer calls `upgradeWebSocket`, the API affected by the 2.0.10 fix — so the *stated benefit* of the `>=2.0.10` floor is also not reached on these paths.

**Verdict: safe, but unsound-by-declaration and not the best available fix.** See finding #400-2 — `>=1.19.13 <2.0.0` would resolve `1.19.17` (a maintained line; npm carries a `latest-1` dist-tag), satisfy **both** consumers' declared ranges, and sidestep the 2.x advisory family entirely. Ask the CVE agent to confirm `1.19.17` is advisory-clean before adopting.

### 3. Recommended merge order: **#400 first, then #387 regenerated.**

**They will conflict.** GitHub reports both `MERGEABLE`/`CLEAN` only because each is evaluated against `master` *independently*. Both diffs edit the same `pnpm-lock.yaml` region — hunk header `@@ -686,14` appears in **both** patches (the `@hono/node-server` block in `packages:`) and each rewrites it differently: #400 → `2.0.12` alone (14 lines → 8); #387 → `2.0.4` + `2.0.12` (14 lines → 14). Whichever lands second gets a conflict there.

**Order rationale — #400 first:**

- #400 carries the security payload. #387 is a proven no-op (see below), so delaying it costs nothing; delaying #400 costs exposure time.
- #387 currently leaves `@hono/node-server@2.0.4` in the tree (the `@prisma/dev` leg). Only #400 removes it. Landing #387 first would leave that version resolved for longer with no compensating benefit.
- After #400, the override floor is `>=2.0.10`, so #387's regenerated lockfile keeps `2.0.12` on every leg and its hono hunk disappears entirely — a smaller, easier second diff.

**Counter-argument, stated honestly:** #387 brings `@modelcontextprotocol/sdk@1.30.0`, which is the only thing that makes the 2.x override *declaration-legal* on the shadcn leg. Landing #387 first would mean #400 never makes the floor explicitly-2.x while a consumer still declares `^1.19.9`. This is a tidiness argument with **no runtime effect** — a declared range is metadata, and the two real v2 breaks are already ruled out above. It does not outweigh shipping the security patch first.

**Does merging one change the other's resolved tree? Yes, materially — in both directions:**

- **#400 → #387**: postcss consolidates to `8.5.25` and hono to `2.0.12` before #387 resolves, so #387's regenerated diff shrinks to shadcn + `@modelcontextprotocol/sdk` + their transitives only.
- **#387 → #400**: `@modelcontextprotocol/sdk@1.30.0` and `hono@4.12.32` land first, so #400's hono hunk reduces to the `@prisma/dev` leg alone.

**Either way, `pnpm-lock.yaml` must be REGENERATED, never text-merged.** A three-way text merge of a pnpm lockfile can produce a syntactically valid file that does not correspond to any real resolution. The second PR's author must re-run resolution on top of the new base and commit that result.

PRIORITY 1 — Block merge, fix first:

  [NEGATIVE SPACE / FALSE ANALOGY LOAD-BEARING IN THE PR BODY]
  PR body + commit body: "Fix mirrors the SePay pattern" / "dispatch on row.adapter === 'vnpay'"

    The SePay analogy is what justifies the whole design, and it does not carry.
    `bank_transfer` is the ONE adapter with no stub twin:
    `app/dev/stub-pay/actions.ts:22` — `STUB_ADAPTERS = { momo, zalopay, card, vnpay }`.
    So `PaymentEvent.adapter === 'bank_transfer'` uniquely implies a SePay-shaped
    body, and `recoverSepayEvent` is safe to key on it.

    `PaymentEvent.adapter === 'vnpay'` carries no such implication. `adapter` records
    the payment METHOD, not the gateway that produced the body. Under `PAYMENTS_STUB`
    — the configuration this deployment currently runs — `submitStubPayment` calls
    `processPaymentWebhook({ rawBody: JSON.stringify(stubIpn), adapter: 'vnpay' })`
    (`app/dev/stub-pay/actions.ts:57-63`), storing a **JSON** `{amount, resultCode}`
    body under `adapter: 'vnpay'`. And VNPay is *offered in the customer UI in exactly
    that mode*: `app/(customer)/booking/review/page.tsx:56` —
    `showVnpay = env.PAYMENTS_STUB || env.VNPAY_ENABLED`.

    Consequence of this diff: those rows now route to `recoverVnpayEvent`, whose
    `URLSearchParams` parse of a JSON string finds no `vnp_ResponseCode`, defaults to
    `'99'` → `unknown` → `{0,false}`. **The sweeper stops recovering stub-vnpay
    bookings that it recovers today** (they currently succeed via the JSON/`resultCode`
    branch), and a stuck one with a lapsed hold goes terminal `payment_failed_expired`.
    That is Bug B, reintroduced onto the currently-active rail by the PR that fixes it
    on the inactive one.

    Neither the PR body nor the commit body mentions the stub path at all. Worse, the
    new adapter test `'does not throw on a JSON body (wrong adapter shape) → { 0, false }'`
    (`lib/payment/__tests__/vnpay.test.ts`) **codifies the regression as intended
    behaviour** — a green test asserting the broken outcome.

    Missing companion (negative space): a sweeper case with `adapter: 'vnpay'` +
    stub-JSON `rawBody`. Absent at every layer — unit (`reconcilePayments.test.ts`
    covers momo + the new urlencoded vnpay), integration (`reconcilePayments.int.test.ts`
    is momo + bank_transfer only), e2e (`vnpay-booking.spec.ts` never runs the sweeper).
    Fully test-blind.

    Fix: the PR must decide and state which key actually determines body shape.
    Options: shape-detect (JSON body → JSON branch regardless of adapter); persist the
    producing gateway alongside `adapter`; or restrict `STUB_ADAPTERS`. Whichever is
    chosen, the body must stop asserting the SePay analogy unqualified, and a
    stub-vnpay sweeper test must land in the same commit.
    → Also filed as P1 [CORRECTNESS] in `docs/qa/code-review-pr357-20260726.md`.

  [PR BODY ACCURACY / SQUASH-MERGE PERMANENCE]
  PR body "## Tests" + commit body paragraph 3

    Claim: "Tests round-trip a REAL adapter-produced body (never a hand-typed shape —
    the trap that hid Bug A/B)."

    True of `lib/payment/__tests__/vnpay.test.ts` (uses `signVnpayBody(baseParams())`,
    the same body the `verifyWebhook` cases prove the real adapter accepts).
    NOT true of the sweeper test this PR adds — `lib/jobs/__tests__/reconcilePayments.test.ts:34-40`
    hand-types `new URLSearchParams({...}).toString()` with its own field subset, no
    `vnp_SecureHash`, and never passes it through `getVnpayAdapter().verifyWebhook`.
    The SePay guard 300 lines below in the SAME file does exactly that (line 372:
    `getBankTransferAdapter().verifyWebhook(sepayRawBody)`), which is the precedent
    being claimed.

    This is a single-commit PR, so squash-merge makes this body the permanent `master`
    commit message — the 2026-07-24 mistake-log rule ("a squash-merge inherits the PR
    body; re-read it against the FINAL diff"). Shipping it tells every future reader
    that a wire-contract round-trip guard protects the sweeper's VNPay path when none
    does, which is precisely how the SePay ref-case bug survived 33 green tests.

    Fix: either make the sweeper fixture adapter-produced (preferred — see code-review
    P2), or narrow the claim to "adapter-level tests round-trip a real body; the sweeper
    case stages a representative querystring."

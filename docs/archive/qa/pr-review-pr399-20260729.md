zero matches across the 10,813 added lines.

**Fix (either is fine, both are cheap):** replace the literal with `ticket.crazyhouse.vn`

### P1-3 · [NEGATIVE SPACE / COMPLIANCE] The PR argues PDPL 2025 in four places and never states a retention period or a deletion path for 14,328 harvested phone numbers

PDPL / Nghị định 13 is cited as the governing authority in `scripts/tourism/README.md`,
`fb_pages_crawl.mts`, `documentation/business/tour-discovery/data-sources.md` (×2) and the
commit-1 message. The compliance section is titled *"Ranh giới đã chốt"* — boundaries
settled — and it settles **collection** limits (no posts, no account names, no faces, no
rating scores, logged-out only) and **publication** limits (gitignored, not committed).

It says nothing about **storage duration**. I grepped the whole diff for retention,
deletion, purge and expiry wording in both languages: the only hits are `docs/qa` artifacts
discussing `CLAUDE.md` length and `lib/jobs/retentionSweeper.ts` (the app's own unrelated
sweeper). For the tourism store there is no retention period, no deletion procedure, no
named owner, and no trigger condition.

Storage limitation is a named PDPL principle, not a nice-to-have, and this repo already has
the machinery and the vocabulary for it (`lib/jobs/retentionSweeper.ts`, a
`/retention-policy` skill, `documentation/` compliance specs). A PR that invokes PDPL as
its central justification and then omits the one principle that governs a 14k-record
personal-data store has an incomplete argument, not merely missing paperwork. And unlike
app data, this store is invisible to every existing control: it is gitignored, so no CI
scan, no audit log, and no `retentionSweeper` reaches it.

**Fix:** five lines in `scripts/tourism/README.md` under *Ranh giới đã chốt* — retention
period (or the event that ends the purpose), the deletion command, who owns it, and where
the store is backed up until then. This is the cheapest P1 in the list and it closes a
statutory gap the PR itself opened.

### P2-2 · [SCOPE] `scripts/audit/secret-scan-staged.sh` + `.husky/pre-commit` is a cross-cutting toolchain change riding inside a data-pipeline PR — and it is the one carve-out with real risk

Asked directly whether the tourism work should split further: **no** for the pipeline and
the `.gitignore` boundary. Those are one change. The boundary is unintelligible without the
thing it excludes, the `.gitignore` comment points at the pipeline's README, and the
`gan_lan_can.py` → `tai_lan_can()` → both renderers chain in commit 6 is correctly
defended in that commit's body — splitting a generator from its only consumer would leave a
script nothing reads. Keep them together.

**Yes** for the secret scanner. It changes the gate that *every commit by every contributor
in this repo* passes through, and it has nothing to do with Đà Lạt. Concretely, why the
ride-along is not free:

- **The failure mode is coupled to the gates it shares a hook with.** `.husky/pre-commit`
  now runs `sh scripts/audit/secret-scan-staged.sh || exit 1` **before** `pnpm lint && pnpm
  tsc --noEmit`. `sk-[A-Za-z0-9]{20,}` is a loose pattern — any 20+ alnum run after a
  literal `sk-` trips it, and there is **no allowlist mechanism at all**, unlike the
  `.gitleaks.toml` this hook is modelled on (which needed 13 allowlist entries and 8 path
  exemptions to be usable). The only escape from a false positive is `git commit
  --no-verify`, which also skips lint and tsc. One false positive trains the author to
  disable all three gates. A fail-closed gate with no exception path is an availability
  risk to the two gates already there.
- **Diagnosis is degraded on purpose.** `grep -I -n -E "$pattern" "$f" >/dev/null 2>&1`
  discards the match; the operator is told the file but not the line or the value.
- **It ships with no test and an unverifiable claim.** Commit 1 says *"Verified firing on
  live keys"* with no artifact. See P2-4.

A dedicated PR would have surfaced all three in review. Inside a 10.8k-line data PR they
are invisible.

**Fix:** cherry-pick the hook + script + the `.husky/pre-commit` line into its own PR with
a fixture test. Note the hook itself is a genuine improvement over CI-only gitleaks and I
am not arguing against it — only against merging it here.

### P2-3 · [NEGATIVE SPACE / `.gitleaks.toml`] The `.gitignore` rationale leans on a gitleaks rule that does not match the shape of the data being protected — and the "Known gap" section discloses the wrong half

The `.gitignore` comment, the README and the PR body all make the same load-bearing
argument: committing is unnecessary to protect because

> `.gitleaks.toml` already has a rule matching that pattern; allowlisting 14k real numbers
> to get a green scan would disable the rule that exists to catch exactly this.

`.gitleaks.toml:8-11` is:

    regex = '''\+84[35789]\d{8}'''

That matches **E.164-normalised mobile** numbers only. It does not match domestic form
(`0903…`), spaced form (`0903 xxx xxx`), parenthesised country code (`(+84) …`), or any
landline (area codes are not in `[35789]`). Vietnamese registers and Facebook Pages publish
in domestic and spaced form; nothing in the pipeline normalises to E.164 before writing
(`parse_fb_pages.py` explicitly notes it folds `+84` vs `0` for *comparison*, not storage).

The proof is in this very diff: the landline in P1-1 sat in a staged, committed file and
neither gitleaks nor the new hook flagged it, because neither pattern matches that shape.
So the second half of the argument — *"allowlisting would disable the rule"* — is
overstated: for most of the 14,328 numbers there is no rule to disable.

The **conclusion** (do not commit the data) is right and I am not disputing it. The
*reason given* is weaker than stated, and the body's self-reported "Known gap" discloses
only the new pre-commit hook's zero PII coverage while leaving the reader believing the CI
scanner covers it. The gap that matters is the one in the control the argument cites.

**Fix:** add a domestic-format rule to `.gitleaks.toml` (`(?<![\d+])0[35789]\d{8}\b`, tuned
against the existing allowlist), or restate the rationale as "no automated control reliably
catches these numbers, which is *why* the directory is excluded rather than scanned" — that
version is both true and a stronger argument.

## PRIORITY 2 — Fix before merge

### 1. [NEGATIVE SPACE / EXTERNAL CALL CONTRACT] New vendor header contract documented nowhere

The PR changes the semantics of an outbound third-party call — every Resend send now carries an `Idempotency-Key`, and the dispatcher's `MAX_ATTEMPTS = 5` retry loop reuses the same key across all attempts. Neither the body nor the code cites Resend's documentation for the two properties the fix depends on: the key's **retention window** and whether a **failed** request may be retried under the same key.

This is the documented half of the same defect `/code-review` raised as its P1 (`docs/qa/code-review-pr346-20260726.md`); it is listed here at P2 to avoid double-counting severity. The repo has been burned by exactly this shape twice — the 2026-07-21 SePay go-live entry ("the exact auth header string and the exact success-ack body must be transcribed from the vendor's live docs and cited in a comment at the verification site").

**Fix:** add the Resend idempotency-key doc URL to the body **and** a call-site comment, and state that the dispatcher's worst-case retry span (`2+4+8+16+30 ≈ 60 min`) fits inside the vendor's key-retention window.

### 2. [NEGATIVE SPACE / TEST PLAN vs STRUCTURAL BLINDNESS] Verify section claims coverage the tests cannot structurally provide

The body's `## Verify — pnpm test` lists two unit-level facts:

> `email.test.ts`: new resend-path cases assert the key reaches `emails.send` …
> `dispatchNotifications.test.ts`: email-route case asserts `idempotencyKey: row.id` is threaded.

Both run against a hand-rolled `vi.mock('resend', ...)` and a hand-built mock row, so they verify the repo's own fixtures, not the vendor boundary or the real persisted row id. Meanwhile `lib/notification/__tests__/dispatchNotifications.int.test.ts` already exists — its header lists "re-run does NOT double-send" and the `@@unique([bookingId, template])` guard as in-scope — and this PR does not touch it.

Direct repo precedent: **#328 (2026-07-25)** was 100% green at unit level because unit tests mock `notificationLog.create`; it only surfaced in `reconcilePayments.int` / `bankTransferWebhook.int` in CI. A "Verify" section that stops at the unit layer for a notification-delivery change repeats that framing.

**Fix:** either extend `dispatchNotifications.int.test.ts` (assert the key equals the DB-assigned row id) and list it in the body, or state in the body why integration coverage adds nothing here.

### 3. [PR BODY / SQUASH-MERGE PERMANENCE] Bug claim stated without its precondition

The body opens by asserting a live defect:

> a crash between the Resend send and the `status='sent'` write re-sends a duplicate customer email on the next cron tick.

True only when `EMAIL_PROVIDER=resend`. The schema default is `'stub'` (`lib/config/env.ts:338`), `.env.example:138-140` ships both `EMAIL_PROVIDER="resend"` and `RESEND_API_KEY` commented out, and under the stub path `sendEmail` returns before `sendViaResend` and drops the key entirely — the fix is inert. The body never states which value production runs.

Per the 2026-07-24 mistake-log entry, on a squash-merge the PR body **becomes the permanent master commit message**, so an unqualified bug claim ships into history and a future bisector cannot tell whether this PR changed prod behaviour at all.

**Fix:** one line — "prod runs `EMAIL_PROVIDER=resend` (email-first launch, #339); under the default stub path this change is inert."

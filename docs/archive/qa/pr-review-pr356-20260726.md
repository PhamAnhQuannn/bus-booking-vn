## PRIORITY 2 — Fix before merge

### [PR DESC / ACCURACY] The stated rationale for the perf rewrite is factually wrong — and it squash-merges into history

Both the PR body and the commit body justify collapsing the per-barrel loop into one alternation
regex with:

> *"the per-barrel loop was ~2k process spawns and **timed CI out on Windows**"*
> *"(the per-barrel loop was ~2k process spawns and **times CI out on Windows**)"*

**CI does not run on Windows.** `.github/workflows/ci.yml:333-335`:

```yaml
  greppable-invariants:
    name: Greppable Invariants
    runs-on: ubuntu-latest
```

There is no Windows runner and no matrix on that job. The slowness is a **local dev-machine**
problem on Git Bash (where process spawns are genuinely expensive), not a CI problem. The real
justification is "unusably slow for local pre-commit use on Windows" — which is a perfectly good
reason, just not the one written down.

Why this is P2 and not a nit: this repo squash-merges, and the CLAUDE.md Mistake Log already
carries the **2026-07-24 entry** on exactly this failure — *"a squash-merge inherits the PR body …
stale/wrong guidance ships into history."* A future reader debugging a G6 false negative will read
"we collapsed this because CI timed out" in `git log` on `master`, conclude the alternation-regex
shape is load-bearing for CI, and be reluctant to unwind it — when in fact that collapse is
precisely what introduced the empty-`alt` vacuous-pass (code-review P1-1). The inaccurate rationale
actively defends the defect.

**Fix:** reword both the PR body and the commit body to "slow on local Git Bash / pre-commit
(~2k spawns); CI is `ubuntu-latest` and was not timing out." One sentence, before squash.

### [NEGATIVE SPACE] Issue #348's Verify step is not delivered in the diff

Issue #348 closes with:

> ## Verify
> **Add** a synthetic `'use client'` file that barrel-imports `@/lib/ledger` and confirm the
> regenerated guard flags it (it currently passes silently).

The PR body reports doing this (`components/__g6probe__/Probe.tsx`) and I independently reproduced
it — the probe genuinely fails under the PR and genuinely passes under `master`. So the *confirm*
half is real. But the **diff contains 1 file and 0 test artifacts**; the probe was transient. Nothing
in the repo re-runs it. `grep -rn "greppable"` across the tree returns exactly one hit —
`.github/workflows/ci.yml:340`. There is no spec, no fixture, no self-test.

The AC wording is arguably ambiguous ("Add … and confirm" reads as either a deliverable or a
verification recipe), so I am not grading this P1 — but the practical consequence is unambiguous:
this PR replaces a list that was **wrong in a visible way** (6 names sitting in the diff, countable
by any reviewer) with a derivation that can be **wrong in an invisible way**, and ships no executable
proof that it still bites. The one artifact that would have made the derivation self-defending was
built, used once, and thrown away.

**Fix:** land a `--self-test` mode in the same PR — write a temp `'use client'` file importing
`@/lib/auth` under a scratch path, assert G6 exits non-zero, delete it, assert G6 exits zero. Wire
it as a second `run:` step in the existing `greppable-invariants` job. That is the issue's Verify
step made permanent, and it also closes code-review P1-1 for the common case.

### [ROLLBACK / OPERABILITY] G6 gains no exemption escape hatch while its blast radius goes 6 → 24 domains

Sibling guard G1 in the same file ships an inline, greppable, per-site escape hatch:

```sh
  | grep -v '// I7-exempt:'
```

so a legitimate exception is annotated **at the violating line**, in the PR that needs it, reviewable
in context. G6 has no equivalent — and this PR quadruples the number of barrels it can fire on
(6 → 24, verified by instrumenting the derivation).

Consequence: the first legitimate exception — a domain that becomes genuinely client-safe, a
deliberate `'use client'` barrel import behind a `next/dynamic` server boundary, or any of the
false-positive classes noted in the code review (multi-line `import type` is a live one) — can only
be resolved by **editing the shared CI script on the blocked PR**. That is a bad shape: it puts an
unrelated author into a repo-wide gate file under time pressure, and it converts a one-line local
annotation into a change that affects every other PR in flight.

This matters more than usual here because the guard now *derives* its own scope: the set it enforces
can change without anyone editing the script, so a future PR can be blocked by a domain that was
untainted last week. There is no documented answer to "G6 just failed and I believe it is wrong."

**Fix:** add a `// @g6-exempt: <reason>` line filter mirroring G1's `// I7-exempt:`, and one line in
the PR body / script comment stating it. Cheap, symmetric with existing convention, and it makes the
exemption itself greppable and auditable.

P1 — BLOCKING:

  lib/core/db/client.ts:14  🐢 P1: `max: 5 → 1` serializes every parallel DB fan-out in the
  application. 32 `Promise.all` sites in `app/` + `lib/` become sequential.

    The diff's own comment states the consequence and then ships it unmeasured:
        "Consequence: `Promise.all([...])` query fan-out serializes on that one
         connection (sum, not max, of latencies)."

    That is not a footnote. Counted across `app/**` and `lib/**` (excluding tests): **32**
    `Promise.all` call sites, and the server-component page shells are the worst of them
    because they were written specifically to parallelize independent reads:

        app/op/(console)/dashboard/page.tsx:55    6 parallel queries
                                                  → snapshot, upcoming, activity, balance,
                                                    busTotal, busActive
        app/admin/(console)/finance/page.tsx:90   4 parallel queries
        app/(customer)/page.tsx:104,176           3 + 3 parallel queries (the landing page)
        app/admin/(console)/page.tsx:92           3 parallel queries
        app/op/(console)/charter/page.tsx:144     3 parallel queries
        app/op/(console)/layout.tsx:42            2 — on EVERY operator console route

    With `max: 1` each of these degrades from `max(t1..tn)` to `Σ(t1..tn)`. For the operator
    dashboard that is a 6× multiplier on database wall time for the page's entire critical
    path. `app/op/(console)/layout.tsx` compounds it: its 2-query fan-out is a fixed tax on
    every operator console page load, serialized ahead of the page's own fan-out.

    Nothing in this PR measures the delta, and no NFR/ADR budget is cited. ADR-002 defines
    NFR targets; this change plausibly breaches page-latency budgets on at least the
    operator dashboard and the customer landing page, and nobody checked.

    Note this is a *separate* cost from the availability failure documented in the
    security-deep review. That one is about contention and the blocking advisory lock
    (#362). This one fires on a completely idle system with one user: sequential is
    sequential regardless of load.

    Fix: before landing, measure the six-query dashboard and the landing page against
    ADR-002's budget at `max: 1`. If the serialization cost is real, the right answer is
    probably not `max: 1` — it is `max: 2..3` (bounded fan-out headroom, still far below
    Neon's per-endpoint connection ceiling), or `unstable_cache` on the fan-out reads.
    "One request per invocation" justifies a small pool; it does not justify 1, because
    one *request* routinely issues six *queries*.

  prisma/schema.prisma:918-919  📇 P2: `@@index([operatorId])` is now a redundant prefix of

    debit, chargeback, and psp_fee writes a row and pays for both indices, forever.

    The same migration drops `Operator_id_idx` with the comment "P1-6: Drop redundant
    Operator.id index (PK already indexed)". The principle is correct and it is applied in
    one place and not the other, 60 lines apart in the same file. If redundant-index
    cleanup is worth a migration line for `Operator`, it is worth one for the ledger.
    Fix: `DROP INDEX IF EXISTS "LedgerEntry_operatorId_idx";` in the same migration, and
    remove `@@index([operatorId])` from the model. Verify first that no query needs a
    different sort order on `operatorId` alone (none found in this audit).

  lib/core/db/client.ts:23  💸 P2: `connectionTimeoutMillis: 3_000 → 10_000` is a direct
  Vercel billing regression on the failure path.

    Vercel bills function invocations by GB-seconds of wall time, and a request blocked
    waiting on `pg.Pool.connect()` is billed for every second it waits. Pre-PR, a starved
    request burned 3s and failed. Post-PR it burns 10s. Under any contention that is a
    3.3× cost multiplier on exactly the requests that produce no value, and it pushes
    requests closer to the function `maxDuration` ceiling — where the failure mode changes
    from a catchable pool error into an opaque platform timeout with no application log.

    The stated rationale — "to absorb Neon autoscale/cold-start latency before a queued
    acquire fails" — is about *cold start*, a first-connection concern. It is being applied
    to *queue depth*, a saturation concern. Those want opposite settings: generous on the
    first connect, aggressive on a queued acquire. `pg.Pool` exposes only the one knob, so
    if cold-start absorption is genuinely needed the honest fix is a warm-up ping or a
    retry around the first acquire, not a 10s ceiling on every acquire for the process
    lifetime.
    Fix: keep 3s in this PR. Justify any increase separately, with the cold-start latency
    actually measured against Neon.

  lib/core/db/holdRepo.ts:89 · prisma/schema.prisma:262-263  📇 P2: The hottest gated query
  in the booking path is still unindexed, in the PR whose stated purpose is index readiness.

        await tx.hold.count({
          where: { customerPhone, status: 'active', expiresAt: { gt: new Date() } },
        });

    This is the concurrent-hold cap. It runs on **every hold creation**, inside the
    transaction, before the advisory lock. `Hold` carries exactly two indices after this
    PR — `(tripId, status, expiresAt)` and the new `(status, expiresAt)` — and
    `customerPhone` leads neither.

    The new `(status, expiresAt)` index does help: the planner can now range-scan
    `status='active' AND expiresAt > now()` and filter on phone. But that index entry set
    is *every active hold across the entire platform*, filtered down to one phone's
    handful. The selective column is `customerPhone` and it is the one not indexed.

    This matters more than a normal missing index because of where it sits: inside the
    transaction that #362 is about, executing before the advisory lock is taken, on the
    single connection this PR reduces the pool to. Every millisecond here is a millisecond
    the sole connection is held.
    Fix: `@@index([customerPhone, status, expiresAt])`. It belongs in this migration —
    it is the same class of change as the other four and it is the one on the hot path.


P3 — ADVISORY:

  prisma/migrations/20260725120000_neon_readiness/migration.sql:14-15  ℹ️  P3:
  `Hold_status_expiresAt_idx` would be materially better as a partial index.

    Both consumers filter `status = 'active'`:
      lib/jobs/expireHolds.ts:23-26  — `WHERE status='active' AND "expiresAt" < NOW()`
      lib/core/db/holdRepo.ts:89     — `{ status: 'active', expiresAt: { gt: now } }`
    Expired, consumed, and released holds accumulate forever and are never queried through
    this index, yet every one of them occupies an entry. A partial index
    (`... WHERE status = 'active'::"HoldStatus"`) stays proportional to the *live* hold
    count — a small, stable, cache-resident set — instead of growing with all-time booking
    volume. The repo already has precedent (Issue 007 shipped two partial indices), and
    CLAUDE.md's rule explicitly allows partial indices to remain SQL-only with no
    `schema.prisma` declaration.
    Fix: optional, but this is the one index here with unbounded growth.

WINS — recorded, no action:

  ✅ `Trip_busId_idx` — genuinely missing. `Trip.busId` is a foreign key, and Postgres does
     NOT auto-index FK columns. It is filtered by the capacity guard (Issue 011), the
     bus-overlap window check (Issue 013 `bus_overlap_with_outbound`), `reassignBus`, and
     `getMaintenanceConflicts`. It also removes the sequential scan Postgres must otherwise
     perform on `Trip` to validate the FK on any `Bus` delete/update. Clear win.

  ✅ `Hold_status_expiresAt_idx` replacing `Hold_expiresAt_idx` — correct column order for
     the sweeper (leading equality on `status`, trailing range on `expiresAt`). Audited all
     `Hold.expiresAt` consumers: none query `expiresAt` without also constraining `status`,
     so dropping the single-column index regresses nothing.

  ✅ `DROP INDEX Operator_id_idx` — `@@index([id])` on a `@id` column is pure duplication of
     the primary key's implicit unique index. Free write-path win on every Operator update.

  ✅ Int → BigInt storage cost: 6 columns × 4 extra bytes per Payout row. Payout is a
     low-cardinality table (one row per completed trip or withdrawal). Negligible.

  ✅ No N+1 introduced. No new unbounded `findMany`. No new `count()` without `where`.
     No new join deeper than 3 levels. No `SELECT *` regression.

# a privacy safety-net written in the WRONG LANGUAGE let personal data onto disk — the guard was language-dependent and the language changed underneath it

Crawling public Facebook Pages for the 36 Đà Lạt places. Facebook's auto-generated *"Unofficial Page"* variants render other users' posts with real names, so the extractor was built to **cut the post region before reading it**, not filter after — cut markers `Posts about` / `Page transparency` / `Privacy` / `All reactions:`, transcribed from the English rendering I had observed through the Playwright MCP browser. But the standalone crawl script set `locale: 'vi-VN'` (correct for a Vietnamese project), so the live pages returned `Bài viết về` / `Tính minh bạch của Trang` / `Quyền riêng tư` / `Tất cả cảm xúc:`. **Not one marker matched. The split was a no-op**, and the evidence files written to disk contained a commenter's name and comment (`Thảo Hà — "Xin giá"`) and a post author (`Dương Ba Gác đang ở Đà Lạt Sử Quán`). Under PDPL 2025 we have no lawful basis to hold any of it. The same locale mismatch also silently mis-*classified* pages: `Trang không chính thức` didn't match `/Unofficial Page/`, so an unofficial page was labelled a managed business Page — a wrong value, not a missing one. Caught by the plan's own verification grep on the 2-page smoke run, before the 35-page run; files deleted immediately. Fix: every marker carries **both** language variants, plus a `POISON` re-check that rejects the whole row if any post residue survives the cut (`đang ở |is at |Bình luận|Comment|Tác giả|Tất cả cảm xúc|All reactions`) — so a future locale or wording change fails loudly instead of silently disarming. **Rule: a safety mechanism that matches on UI text is only as good as the locale it was written against — and locale is configuration, set far from the guard it breaks. Any guard keyed on rendered strings must (a) cover every locale the caller can request, and (b) be backed by a positive assertion that the guard actually fired, because "the regex matched nothing" and "there was nothing to match" are indistinguishable from the outside. Greppable smell: a `split()`/`indexOf` on user-visible UI text in the same file as a `locale:` option, with no post-condition check.** Corollary on where the check belongs: the identical field-extraction logic first lived inside `page.evaluate`, so every fix cost 35 real page loads — and it was wrong three times (esbuild's injected `__name` helper is undefined in the browser when `page.evaluate(fn)` ships a *named* function's source; a string argument is evaluated as an *expression*, so `"() => {…}"` returns an uncalled function and yields `undefined`; then the phone regex grabbed a number out of prose instead of the structured field). Splitting fetch-and-save from parse (`fb_pages_crawl.mts` → `raw/pages/*.txt` → `parse_fb_pages.py`) made every later fix a free offline re-run and left exactly **one** parser for those bytes — the same one-producer-two-consumers discipline the 26/07 VNPay differential entry demands.

# the official star ranking was never in the data we hold, the script that "extracts" it has always returned None for every row, and the site is now 403 so we cannot go back for it

Asked whether OTA APIs (Traveloka/Expedia/Booking) could supply hotels by price band and reviews. The repo's own five-seat debate (`documentation/business/tour-discovery/data-sources.md`) already answered it: scraping those sites is in the *Explicitly out* list; affiliate APIs give links and live rates but ban data-forwarding; only **Hotelbeds Content API** (terms *require* storing + weekly refresh) and **Agoda Partner API** are storable, both contracted-partner tiers; reviews are blocked everywhere (TripAdvisor gives them free but only `location_id` is cacheable). That document also names the better answer for the price/tier question: Vietnamese law requires the tourism authority to publish the **ranked** accommodation list, and *"that list IS the 5★ → mid → low stratification — official, free, one source two jobs."* Chasing it produced three findings in a row, each invalidating the plan built on the last. (1) **`sweep_csdl_stars.py` was already known unusable** — it fires 7 `rate[]` queries and keeps only the per-tier `total` plus 6 truncated sample strings, so the star label belongs to the response batch, not to any record. Its numbers are also not credible: `5 sao = 294` across three provinces. (2) **`sweep_csdl.py` contains a `star(t)` helper that greps `"5 sao"`…`"1 sao"` out of each row's text — and it has always returned `None` for all 1.230 rows.** Measured just now against the stored raw: **0/1.230 contain any `N sao` token**; the listing text carries only name, address, and `"Cơ sở lưu trú tự đăng ký"` / `"Thông tin do Cơ quan nhà nước"`. Every `sao` substring in the corpus is a hotel *named* `Sao Vàng`, `Sao Kim`, `Sao Biển` — a proper noun, the same name-vs-category collision this project has now hit at the dish layer (`Chè hé`), the toponym layer (`Nhà Chung`), and here at the rank layer. The script printed `không xếp hạng: 1230` every run and nobody read it as "this field does not exist here". (3) **The site now returns 403 to everything** — `/cslt/`, `/`, and `robots.txt` itself, blanket, with our polite UA that worked on 28/07. **I did not change the User-Agent.** A 403 on `robots.txt` means the access policy cannot even be read, so no compliance claim is possible; disguising the client after being refused is circumventing an access control, which is precisely what this project's scraper-ethics posture rules out, and there is already one unresolved robots.txt finding open against the Facebook crawler. **Rule: a helper that extracts a field is not evidence the field exists — check its hit rate against the stored corpus before planning on it. `star()` looked like working code, sat in a script that ran successfully, and had a 0% yield since the day it was written; the tell was printed on every run and read by nobody. Greppable smell: an extractor whose "not found" branch returns a bare `None`/`0` with no count of how often that branch is taken. And: when a source starts returning 403 — especially on `robots.txt` — the polite path is to stop and request access, not to re-dress the client. A source that worked three days ago is not a source you still have.** Consequence recorded so the next round does not re-plan on it: the **official star tier is not obtainable**; the 1.230 rows collected on 28/07 remain usable but will never gain a rank; hotel tiering stays on `gia_min` (213/420) with 207 honestly labelled "không công bố giá"; reviews remain unavailable on every free and self-serve paid route. If the ranked list genuinely matters, the legitimate route is a data-access request to the agency, not a scraper.

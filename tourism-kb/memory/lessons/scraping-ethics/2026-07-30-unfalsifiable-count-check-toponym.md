# I wrote a regression check that compares a COUNT across two runs against a corpus that changes underneath it — the check was unfalsifiable, and a TOPONYM-as-business-name hole it could never have caught was sitting in the output

Re-ran `sweep_youtube_quan.py` after the v1 result (72 rows) had been destroyed by a truncated run. Wrote four acceptance checks into the plan beforehand. Two were sound, two were not, and the difference is the lesson. **Sound:** *"`Bánh canh Xuân An` must not be attributed the dish `Bánh căn`"* — a within-run test of one row's attribution, decidable from a single run's output; it **passed** (it got `Bánh mì`, `Bánh mì xíu mại`). *"every row must carry `dia_chi` or NULL, never a guess"* — decidable; **39/41 have an address, 2 are NULL** (`Phường 7`, `Đà Lạt Sử Quán`), which is the correct behaviour. **Unsound:** *"`Bánh Căn Lệ` must show ≤ 8 videos"* (it showed **10**) and *"row count must be ≥ 72"* (it was **41**). Both compare a count from THIS run against a count from a PRIOR run, but `search.list` returns different videos every day and the 72-row artifact no longer exists to diff against — so neither number can distinguish "the matcher regressed" from "YouTube returned different videos". I could not evaluate my own checks, and the tempting move was to explain the gap away with a plausible mechanism ("v2 matches per-field and by word boundary, so fewer is expected") — which is a hypothesis, not a measurement, and is exactly the error already logged one entry down about audit findings that arrive with a real count attached. Recorded as unevaluable rather than as pass or fail. **Rule: an acceptance check must be decidable from the artifact it is run against. A threshold on a count drawn from a NON-REPRODUCIBLE upstream (a search API, a live feed, a crawl) is not a regression test — it cannot fail for the reason you wrote it, and it will "fail" for reasons you did not. Test the invariant instead of the magnitude: which dish a row is attributed, whether a field is NULL vs guessed, whether every name resolves in the dictionary. Greppable smell: an expected value in a plan or test that was read off a previous run's console output rather than derived from a rule.** What the checks missed, found only by printing all 41 rows and then measuring a specific suspicion: **the ≥2-independent-channel threshold measures NOTABILITY and says nothing about IDENTITY.** `Nhà Chung` (coffee_shop) sits at **`8 Hẻm 6 Đường Nhà Chung`** and `Phù Đổng` (diner) at **`37 Đường Phù Đổng Thiên Vương`** — each business's own name is contained in its own address, because it is named after the street it stands on. A vlogger saying *"quán bánh căn ở Nhà Chung"* means the STREET, and the same list separately contains `Bánh căn Nhà Chung` at `1 Đường Nhà Chung` and `Bánh canh Xuân An` at `15B Đường Nhà Chung` — so the street really does hold several eateries, which is precisely why vlogs name it. Same class: `Phường 7` and `Phường 9` are WARD names that are also registered business names, and both cleared the threshold. The script's `CHUNG` stoplist rejected 257 all-generic names, but these are not generic — they are specific proper nouns that denote a place rather than a business, which no frequency or genericness test can separate. **Rule: a name-matching dictionary built over businesses must screen for names that are TOPONYMS — street, ward, district, landmark. Cheap decisive test, one line: fold the name and ask whether it appears inside its own address; a business named after its own street will match, and the mention that "found" it is at least as likely to be about the location as about the shop. Greppable smell: a matched entity whose `name` is a substring of its own `address`.** Third occurrence in this project of one string being simultaneously a category and a proper noun (`Chè hé` the shop harvested into the dish-token set; `Đà Lạt` the city inside hundreds of business names); this is the same trap arriving at a third position — the toponym layer.

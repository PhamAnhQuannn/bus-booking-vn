# the .docx build CRASHED, the .md had already been rewritten, and `kiem_parity.py` looked at the mismatched pair and said `KHỚP` — exit 0

Re-rendered the Đà Lạt guide after adding a toponym filter to the vlog layer (41 eateries → 37). `build_huong_dan.py` wrote the `.md` fine. `build_huong_dan_docx.py` then died with `PermissionError: [Errno 13] ... 'docs/Huong-Dan-Da-Lat.docx'` because the file was open in Word (`docs/~$ong-Dan-Da-Lat.docx` lock file present), so the `.docx` on disk stayed at the **previous day's** content. Ran the parity guard on that pair and it printed `KHỚP — hai ban dau ra khong lech o diem nao duoc kiem` and exited 0. Measured the divergence it missed by counting content markers in both files directly: `Nhà Chung` **3 in .md vs 1 in .docx**, `Bánh Căn Lệ` **3 vs 1**, `Lẩu Gà Lá É Tao Ngộ` **6 vs 2**. Two independent causes, either alone enough for a false pass. (1) **No freshness check exists** — grepping all 226 lines of `kiem_parity.py` for `getmtime|os.stat|st_mtime` returns nothing, so "the `.docx` is a day older than the `.md`" is not a thing the guard can express, let alone detect. (2) **The food layer is entirely outside its coverage** — grepping the same file for `quán|món|ẩm thực|quan_vlog|kênh` returns **zero lines**. It compares section titles, the top-level numbering sequence and the set of `mục N` cross-references; the change I had just made lives wholly inside the eatery section, which it never looks at. The guard was not defeated by anything subtle — it was asked a question it does not ask. **Rule: a pipeline where step 2 can fail after step 1 has already written its output MUST NOT let step 3 bless the result — a crashed renderer leaves a half-updated output set, and a checker with no freshness test will pass it. Make the check refuse to run when its inputs are not from the same build: compare mtimes, or have every builder stamp a shared run id into its output and require the ids to match. And a cross-output checker must state which layers it does NOT compare; "KHỚP" with no coverage statement reads as "these documents agree" when it means "the six things I look at agree". Greppable smell: a parity/diff/consistency checker that takes two file paths and never reads their mtimes, and whose marker list was hand-written once against the document skeleton rather than derived from the sections the builders actually emit.** This is the **third** variant of one weakness in three days: 30/07 morning — the guard cannot see an error *upstream* of the split (both outputs read one `guide_data.json`, so a wrong value renders identically in both); 30/07 later — its per-marker test was `both present` rather than `counts equal`, so a warning rendering 3× vs 2× passed; now — it cannot see that one output is simply **stale**, nor look at the layer that changed. Each fix addressed the instance, not the shape, and the shape is: *the guard's question set is fixed and hand-written while the documents' content is generated and grows.* The correct fix is to derive the comparison set from what the builders emit, not to add a seventh hand-written marker. Note what did work, and why: the toponym filter was proven to fire before being trusted — it printed all 4 dropped rows with reasons, `Bánh căn Nhà Chung` correctly survived (it carries a distinguishing token outside the street name), and 0 rows with `fold(ten) ⊂ fold(dia_chi)` remained. That check was written to be decidable from a single run, which is exactly what the entry below requires of an acceptance check.

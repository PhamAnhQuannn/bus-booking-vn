# I read the warning about category-word prefixes in this same session, then wrote the matcher without it — 8 correct hotels rejected at 3–20 m; and my acceptance test's EXPECTATION was wrong, not the code

`sweep_google_placeid.py` resolves a Google `place_id` per establishment so the guide can emit a link that points at the business instead of dropping a pin on a coordinate. Acceptance is deliberately two axes (name + position). First real run: **16/47**. The rejection reasons were the finding: `Khách sạn Bồ Công Anh` 10 m ↔ `Bo Cong Anh Hotel`, `Khách sạn An Phú` **3 m** ↔ `An Phú Hotel - Đà Lạt`, `Khách sạn Tamy` 13 m ↔ `TAMY Hotel`, `Khách sạn La Sapinette Đà Lạt` 12 m ↔ `La Sapinette Hotel Da Lat`, `Khách sạn biệt thự Liên Hương` 6 m ↔ `Liên Hương Villa` — eight rows, all unambiguously the same building, all rejected because the register writes `Khách sạn X` while Google writes `X Hotel`, and `tim_cum` needs one folded string to contain the other. **`sweep_luu_tru.py`'s own docstring says exactly this** — *"gần như mọi tên đều mở đầu bằng từ chỉ LOẠI… bỏ từ đó đi rồi mới so — nếu không thì mọi khách sạn đều giống mọi khách sạn"* — and I had read that file earlier in the same session while checking how the lodging register was parsed. Stripping category words from both sides took 16 → **24**. **Rule: a warning written in the docstring of the module that produced your input data is part of that data's contract. Before writing any matcher against a dataset, grep the sweep that built it for the words `bay`/`bẫy`/`trap`/`⚠` — the person who parsed it already met the failure you are about to re-enter. Greppable smell: a new name-matching function whose token/substring rule was designed from the shape of the *query* names rather than from a read of how the *stored* names are actually formed.** Two further corrections in the same pass, both mine. (1) The position axis was written `if coords: distance elif address: street` — so a stale coordinate **vetoed** better evidence; `Palace Heritage` (611 m), `Hương Giang` (491 m), `Hữu Nghị 2` (823 m) all had a house number that matches. Changed to *distance OR address*; still two axes, one of which simply accepts two forms of evidence. (2) **My acceptance test asserted the wrong expectation.** It flagged `Bánh căn Ngọc` ↔ `Bánh căn Ngọc Hà` as a false positive, so I tightened the final comparison from substring to equality — which cost a genuine match (`TTC Premium` vs `TTC`). Tracing it: that pair matches in the *original* `tim_cum` pass, whose word-bounded-prefix behaviour is **intended** (`Bánh Căn Lệ` ⊂ `Bánh Căn Lệ - Chi nhánh 2`, `Kem Phụng` ⊂ `Kem Phụng Đà Lạt` are the same business under a fuller name). The code was right and the test was wrong, and I changed the code first. **Corollary rule: when a self-written check fails, establish WHICH code path produced the result before changing anything — a failing assertion is evidence about the pair (test, code), not about the code alone.** Final: **25/47 (53%)**, remaining split 12 name-matches-but-position-doesn't · 5 position-matches-but-name-differs · 5 no candidate. Stopped tuning there deliberately: past that point every fix chases one row, which is the pattern criticised two entries down. Storage discipline held throughout — `place_id.json` greps clean for `rating`, `userRatingCount`, `formattedAddress`, `displayName`, `priceLevel`, `location`; Google's own strings live only inside the matching function. **Scope gap to record: the DL-15 regression case I declared mandatory could not run** — the 47 rows are 17 restaurants + 30 lodgings, and DL-15 is a *destination*; the 36 destinations were never added to the resolve set even though the coordinate-link defect that motivated `place_id` is theirs. A stated acceptance test that the built artifact cannot exercise is not a passing test, it is an absent one.

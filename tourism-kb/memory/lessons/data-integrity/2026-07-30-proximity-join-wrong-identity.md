# a proximity matcher with no identity test gave five destinations someone else's opening hours — and the "second source" confirming one of them was the same source counted twice

`enrich_osm_ondisk.best_match` takes the **nearest OSM element within 300 m, name-agnostic**; the name test at `:61` only *widens* the radius to 600 m when names agree, it never *requires* agreement. So any destination whose own OSM node is missing silently inherits a neighbour's identity, and five did, all the way into the published `.md`: **Hồ Xuân Hương** took its address, Vietnamese name and `Giờ mở cửa 06:00-24:00` from **`Coffee One Day`, 113 m away** — a lake with opening hours; **Khu Di Tích Dinh Bảo Đại** took the **Lam Đồng Museum's** hours and English name at 183 m; **Dinh Bảo Đại 1** took hours/website/wifi from a facility inside the grounds at 211 m; **Làng Cù Lần** — which is 20 km out in Lạc Dương — took `12 Lữ Gia`, `24/7` and a personal gmail from a city-centre POI at 114 m; and **Chùa Linh Phước**, a pagoda, took `Room: 19; Price: 48-198 USD/night`, a star rating and wifi from a **hotel** 50 m away. The sharpest one is DL-01: XQ Sử Quán's house number `258` came from a node **89 m** off, and `dia_chi_day_du` *looks* like an independent second source agreeing with it but is that same node's number plus Nominatim reverse-geocoding **our own stored coordinate** — one origin printed twice, while Wikipedia's `80A` is the only independent statement. An external reviewer flagged the 80A/258 conflict as "Wikipedia vs the map dataset"; it is not, and treating it that way would have "resolved" it toward the wrong number. **Rule: distance is not identity. A spatial join may only fill a field that describes the ENTITY (hours, address, contact, amenities, names in the local language) when the match is corroborated by something other than proximity; naming/reference fields that legitimately sit far away (`name:en` of a lake, a Wikidata QID, a centroid) are the only ones a radius alone may carry. And the verdict belongs to the ELEMENT, not the row: if one field from an element fails the test the element is not this place, so its name is not this place's name either — that is what separates "Lam Dong Museum" at 183 m (rejected) from "Valley of Love" at 215 m (kept). Greppable smell: a `best_match`/`nearest` returning the closest record within a radius, where the name check appears only in the branch that RELAXES the radius. Corollary on corroboration: before counting two fields as two sources, trace both to their origin — a reverse-geocode of your own coordinate is your own coordinate, not a witness.** Two compounding defects surfaced in the same pass. (1) **Precedence was inverted**: `build_huong_dan.py` rendered `r["hours"]` (merge layer, no source, no date) in preference to the `enrichment.json` row (source + URL + date), so DL-32 Bảo tàng Lâm Đồng printed an OSM string while its own enrichment row — the ⚠ recording that the museum's homepage and ticket page state different hours, the finding logged on 28/07 — was dropped in silence. *A value with provenance must not lose to a value without it; when both exist and differ, the disagreement is the finding and both get shown.* (2) The self-audit table counted `r["hours"]` alone and reported **`Có giờ mở cửa: 5`** while the document actually printed **11** — a verification table under-reporting the very document that contains it. Both renderers had each defect independently, so the fix lives in `an_ngu_data` (`loc_khop_xa`, `gio_bi_loai`, `co_gio_mo_cua`) and both builders call it. Note what did NOT catch this: `kiem_parity.py` passed throughout, correctly — it compares the `.md` against the `.docx`, and both read one `guide_data.json`, so a wrong value renders identically in both and parity is silent by construction. **A cross-output parity check cannot see an error upstream of the split; that class needs a check that reads the INPUTS.**
